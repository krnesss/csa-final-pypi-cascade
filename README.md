# 一个底层包的漏洞，怎样级联到整个生态？

> **复杂系统分析 · 期末项目** · 选题 Q4
> PyPI 依赖网络中的影响传播、瓶颈识别与韧性情景实验
> 数据快照：**2026-11** ｜ 15,780 个包 ｜ 47,944 条依赖边 ｜ 26,810 条安全公告

---

## 三条结论（先看这个）

| 数字 | 含义 |
|---|---|
| **108.7×** | 在**同一份模型内部**，忽略漏洞版本区间的结构命中数（1,188,370 对）是版本感知命中数（10,931 对）的 108.7 倍。**这是两个口径之间的倍数，不是"真实世界风险被高估 108.7 倍"。** 详见下方「口径必须写清分母」 |
| **41.8 pp** | 如果把食物网的"或门"级联规则搬到软件（软件是"与门"），韧性会被高估的百分点数 |
| **47.6× → 1.85×** | **本轮最重要的修正**。把"谁连谁"随机化但保持度序列后，反向可达均值从真实的 **11.08** 涨到朴素族 **526.92 ± 94.85**（**47.6 倍**）；但这个暴涨里绝大部分是**保度交换自己制造出来的巨型强连通分量**（朴素族最大 SCC 中位数 **484** 个节点，真实图只有 **8**）。用**保环（保序）零模型**剥掉这一项后是 **20.53 ± 1.53（1.85 倍）** —— 真实拓扑本身的贡献只有这个量级。原报告"38–57 倍"与"随机故障下近 6 倍鲁棒"的结论**已撤回**，见 `report/03_结果.md` §6.1 |

**对一个底层包漏洞的定量回答**：平均波及 **9.75** 个种子包（图口径 11.08），最坏 **4,316** 个（`typing-extensions` = 全生态 27.4%），
最深 **20** 跳；前 0.5% 的 79 个包承担 **51.0%** 的潜在波及量。

## 口径必须写清分母（这是本项目最容易读错的地方）

三级口径 S / F / V 与它们之间的两个收缩率，**回答的是三个不同的问题**：

| 收缩 | 公式 | 分母 | 它实际说的是什么 |
|---|---|---|---|
| S → F | (S−F)/S = **9.47%** | **S** | 把 OSV 的 `fixed` 边界抹掉后命中几乎不变 ⇒ 几乎所有结构命中本来就落在 `≥introduced` 一侧。这一步**与"依赖者是否升级"无关**——S 口径里根本没有 fixed 这个概念 |
| F → V | (F−V)/F = **98.98%** | **F** | 命中集合从「`≥introduced`」收缩到「落在脆弱区间内」。在单区间的 advisory 上，这个差集**恒等于**「`resolved ≥ fixed`」——这是一条可以逐条核对的**定义恒等式**，不是机制发现 |

因此下面这句话是**错的**（本项目早期版本在 README、`report/03`、`report/04`、PPT 里都写过）：

> ~~"98.9% 的高估来自依赖者早已升级越过修复版本"~~

正确的写法是：

> 在本项目的 PyPI 种子样本与当期依赖解析快照中，忽略漏洞版本区间的结构命中数约为版本感知
> 命中数的 **108.7 倍**。进一步引入"假设漏洞引入后一直未修复"的反事实口径 F 后，S→F 只减少
> 约 **9.47%**（分母 S），F→V 再减少约 **98.98%**（分母 F）。
> 这说明"OSV 修复边界 × 当期解析版本"这个组合显著收缩了**模型口径**下的暴露面；
> **不能据此证明真实部署中的漏洞风险被高估 108.7 倍，更不能证明依赖者实际完成了对应比例的升级。**
> 我们只有当期快照，没有时间序列，因此**无法观察"谁在何时升级"**。

唯一能把"结构扫描到底准不准"讲清楚的地方，是那 **25 条至今没有补丁**（区间未封口）的
advisory：在它们上面 S / V 只有 **1.23×**。也就是说，**当漏洞真的还没被修时，朴素结构扫描是准的；
它的错，恰恰错在把"已修的历史存量"当成了"当前风险"。**

**这一版做了一个会被扣分的决定**：我们把上一版的一条主要结论**撤回**了。

## 数据质量记账（不是"数据很干净"，而是"脏在哪、有多少"）

课程要求"解释节点、边与权重"；本项目额外要求自己**把数据的缺陷变成表里的一个数字**。

| 记账项 | 说明 | 出处 |
|---|---|---|
| `seeds_resolved_ok` / `seeds_unresolved_fallback` / `seeds_missing` | 种子包的三分：deps.dev 已解析 / 只能回退到 PyPI 声明层 / 完全缺失。**"抓取失败"从不被当成"没有依赖"** | `graph_stats.json` |
| `seeds_strict_complete` | 严格完整 = 已解析 **且** 图级无错 **且** 无节点级错误。早期版本把 `deps_status=ok` 直接当成"闭包完整"，是过度声称 | `graph_stats.json` |
| `seeds_with_graph_error` / `node_level_errors_total` | 逐条保留 deps.dev 返回的图级 `error` 与节点级 `errors` 原文，而不是丢弃 | `data/raw/depsdev_deps.jsonl` |
| `fallback_fetch_failed` vs `fallback_no_requires_dist` | 回退时**区分**"PyPI 明确没有依赖"与"PyPI 请求失败"——两者都表现为空列表，但含义完全相反 | `graph_stats.json` |
| `fallback_marker_environment` | 回退源的 PEP 508 marker 在**显式固定的基准环境**（python 3.11.9 / linux / cpython / 无 extra）里求值，不再只看字符串里有没有 `extra` | `config/config.yaml` |
| `t11_closure_vs_graph.csv` | 闭包口径与图口径在**同一总体**（图内种子）上的集合比对：`only_closure` / `only_graph` / Jaccard，把"叶子截断"与"声明层回退"造成的偏差量化 | `results/tables` |
| `t29_edge_spotcheck.csv` | 三层分层抽样的边清单，带 deps.dev / PyPI 直链与待人工回填的 verdict 列——交付的是**可被独立核对**的凭证 | `results/tables` |
| `t26_protocol_check.json` | 内含一个两节点反例自检：`A→B, C→B` 删掉 A 后 B 的入度由 2 变 1。**用来钉死一个曾经写错的断言** | `results/tables` |

## 一键复现

```powershell
cd project
powershell -NoProfile -ExecutionPolicy Bypass -File .\run_all.ps1             # 全流程（含约 50 分钟 API 抓取）
powershell -NoProfile -ExecutionPolicy Bypass -File .\run_all.ps1 -SkipFetch  # 数据已就位，只重跑分析
python -X utf8 tests/test_small_graphs.py                                    # 只跑小图手算测试
python -X utf8 src/50_verify_numbers.py                                      # 只核对正文数字与结果表是否一致
python -X utf8 src/40_make_pptx.py                                           # 单独重新生成 PPT
```

> 脚本内部固定 `PYTHONHASHSEED=0`。原因见 `report/02_数据与方法.md` §5.2：
> 零模型的边随机化从一个 `set` 起步，不固定哈希种子会让同一 seed 在不同进程间
> 相差约 0.02%。固定后**端到端重跑逐位一致**。

**为什么先跑测试**：`run_all.ps1` 的第一步是 `tests/test_small_graphs.py`。
它用**手算得出期望值**的小图（链、菱形、森林、3-环、双父节点反例）验证位集可达、
SCC 凝缩、级联深度、OR/AND 规则、保度交换、平局排序这七件事。
这些算法错了不会让指标"看起来不对"——只会让指标**看起来很漂亮**。
跑不过就 `exit 1`，后面的分析一步都不许跑。

**环境**：Python 3.13 + `networkx pandas numpy scipy matplotlib packaging pyarrow pyyaml python-pptx pillow`

**数据来源**（全部公开、无需密钥、无需登录）：
* PyPI 月下载量榜：`hugovk.github.io/top-pypi-packages`（镜像 pypistats 的 ClickHouse 统计）
* 依赖图：`api.deps.dev/v3`（Google osv-scanner 团队）—— 返回**已解析**依赖闭包
* 漏洞库：`osv-vulnerabilities.storage.googleapis.com/PyPI/all.zip`

## 关键口径（读结果前必看）

| 口径 | 定义 | 用在哪 |
|---|---|---|
| **依赖流方向** | 边 `u → v` 表示 **u 依赖 v**，于是 `in_degree(v)` = 直接依赖 v 的包数、`out_degree(v)` = v 直接依赖的包数。**不能反过来** | 建图与全部中心性 |
| **级联传播方向** | 与依赖流**相反**：v 出问题 → 传播到所有**传递依赖 v** 的包 | 所有影响面指标 |
| **闭包口径（精确）** | 用 deps.dev 的已解析闭包统计"被多少种子包传递依赖" | `n_transitive_dependents`，主口径 |
| **图口径** | 直接边图上的反向可达集；与闭包口径在**同一总体**上比对（见 `t11`） | `n_transitive_all_nodes` |
| **R_AND（软件真实）** | 任一直接依赖坏 ⇒ 包坏 | 韧性实验主口径 |
| **R_OR（食物网）** | 全部直接依赖坏 ⇒ 包坏 | 韧性实验对照 |
| **三级漏洞口径** | S 结构上界 / F 反事实未修复 / V 现实版本感知。**三者分母不同，见上表** | 实验三 |
| **PageRank 方向** | `pagerank_importance` 算在依赖流图上（"被谁依赖"）；`pagerank_inherited` 算在反向图（"依赖了谁"）。两者几乎正交，**方向搞反结论反掉** | 指标一致性 |
| **介数中心性** | 主流程用**精确全源介数**（`config: betweenness_k=0`，本图约 50 s）。采样近似只作为"如果当初偷懒会错多少"的敏感性证据保留 | `t27` |

## 三条必须写在结论旁边的限定

1. **没做方法级可达性分析**。版本脆弱 ≠ 代码真的调用了脆弱函数。所有"影响面"都是**上界**。
2. **现实口径衡量的是"今天全新解析（fresh install）"**，不是"所有已部署环境"。
   大量用户 pin 在旧版本，那部分存量风险不在该口径内。**我们也没有时间序列，
   无法观察升级行为。**
3. **拓扑指标的预测力只有 ρ ≈ 0.4**，且随时间距离单调上升（0.37 → 0.49）。
   它是"仍然活着的风险的排序器"，**不是"未来漏洞风险预测器"**。
