> **数值口径声明**：本文所有数字来自一次固定的时间切片（2026-11）与固定的随机种子
> （`config/config.yaml` + `PYTHONHASHSEED=0`）。端到端重跑逐位一致。

**一句话结论**

> 在 2026-11 这个时间切片上（15,780 个包、47,944 条依赖边、14,992 个种子包），
> 一个底层包出问题后平均会**波及 9.75 个包**、最坏**4,316 个**、最深**20 跳**；
> 排名前 0.5% 的 79 个包承担了**51.0%** 的全部潜在波及量。
> 结构命中数（1,188,370 对）是**版本感知**命中数（10,931 对）的 **108.7 倍**——
> 注意这是**两个口径之间的倍数，不是"真实世界风险被高估 108.7 倍"**，口径拆分见 §4。
> 并且：**软件依赖是"与门"**，所以按食物网（"或门"）的级联规则建模会让
> 韧性被高估 **41.8 个百分点**。最后一条是本轮被自己推翻又重建的：
> 把"谁连谁"随机化但保持度序列后，平均级联规模从 **11.08** 涨到 **526.92 ± 94.85（47.6 倍）**，
> 但其中约 **98%** 是零模型自己造出来的**巨型环**（最大 SCC 中位数 484 个节点，真实图只有 8）；
> 换成**保环零模型**后真实拓扑只贡献 **1.85 倍**（20.53 ± 1.53）。详见 §6.1，
> 并请一并看 §8 的 H5 / H6 两条"已撤回"的假设。

## 1. 结构：这是一个什么样子的网络（RQ0）

### 1.1 基本规模

| 指标 | 数值 | 解读 |
|---|---|---|
| 节点 / 边 | 15,780 / 47,944 | 稀疏有向图，密度 1.9×10⁻⁴ |
| 平均度（入=出） | 3.04 | 每个包平均依赖 3 个包 |
| 最大弱连通分量 | 12,581（**79.7%**） | 存在一个巨大的主连通块 |
| 孤立节点 | 2,719（17.2%） | 无依赖也无依赖者 |
| 度同配性 | **−0.148** | **异配**：枢纽包被大量低度包依赖，高度包之间互相不依赖 |
| 非平凡强连通分量 | 20 个，最大 8 个节点 | 条件依赖互相引用造成的小环 |
| 依赖深度（包 → 最深依赖） | 均值 **2.26**，p50 = 2，p95 = 6.45，max = 20 | **浅**：绝大多数包的依赖链很短 |
| Gini(入度) | **0.909** | 极度集中 |

### 1.2 度分布：入度重尾，出度窄（图 1）

| 分位数 | 入度（被依赖） | 出度（依赖别人） |
|---|---|---|
| 均值 | 3.04 | 3.04 |
| p50 | **0** | 1 |
| p90 | 3 | 7 |
| p99 | 42 | 26 |
| max | **1,604**（numpy） | 157 |

* 入度与出度**均值恰好相同**（每条边贡献一次），但分布形状完全不同：
  入度是极端重尾（56.4% 的包没有任何包依赖它），出度则是窄分布（多数包只依赖 1–3 个）。
* **按课程提醒，我们不做"幂律"断言**：长尾外观不足以证明幂律，
  这里只把"重尾 + 高 Gini"作为描述性事实，并交给零模型去判别它的后果（§6）。

### 1.3 两层口径的一致性：**必须在同一总体上比**（评审意见 A-02 / B-03）

广度有两个独立实现：

* **闭包口径**：用 deps.dev 的已解析闭包直接数"被多少种子包传递依赖"；
* **图口径**：在直接边图上做反向可达（用 `uint64` 位集向上合并）。

**它们不是同一个总体**：闭包记录只覆盖 14,992 个**种子包**，而图里还有 788 个
**榜外叶子**（`nodes.csv` 的 `expansion = boundary_not_expanded`，我们没抓它们的出边）。
所以早期版本里"闭包口径 N vs 图口径 M"的对照表是**两个不同总体相减**，
不能用来归因于任何一类错误。为此新增 `src/11_closure_vs_graph.py`，
把总体对齐到"图内种子"这一个共同集合，对每个包 v 比较两个**集合**：

```
A(v) = { s ∈ S : v ∈ closure(s) }         闭包口径
B(v) = { s ∈ S : s 在图中反向可达 v }      图口径
```

| 指标 | 含义 | 数值 |
|---|---|---|
| `total_both_pairs` | 两个口径都认为"该种子依赖 v"的 (包, 种子) 对 | **141,342** |
| `total_only_closure_pairs` | **闭包说有、图说没有**（图漏层 / 叶子截断） = FN | **12,567** |
| `total_only_graph_pairs` | **图说有、闭包说没有**（声明层回退边 / 包名合并造成的假路径） = FP | **48,487** |
| 召回 / 精确率 | `both/(both+FN)` 与 `both/(both+FP)` | **91.8%** / **74.5%** |
| `jaccard_median` / `jaccard_p05` / `jaccard_mean` | 集合级重合度（不是大小差） | **0.667** / 0.333 / 0.636 |
| 有符号差（图 − 闭包） | 中位数 / 均值 / p05 / p95；正 / 负 / 零 占比 | **1** / 2.28 / 0 / 3；92.9% / 2.2% / 4.8% |
| **绝对差** | 中位数 / p90 / p95 / p99 / max | **1** / 2 / 3 / 42 / **944** |
| 共同总体上的 Spearman | 两个口径的**秩**一致性 | **0.931** |
| `sensitivity` | 只保留"严格完整"种子时的 Spearman 与 Top-20 重合 | 见下 |

**读到两个必须说的话**：

1. **正差占 92.9%、负差只占 2.2%**：
   图口径**系统性地比闭包口径大**。原因不是"图更全"，而是图里多了
   **DIRECT_DECLARED 回退边**（8,639 个包只有图口径能找到依赖者，
   它们几乎全部来自这一层）。这正好说明为什么"两个口径的数字不能直接相减"。
2. **绝对差的中位数只有 1，但 p99 是 42、最大 944**：
   绝大多数包的两种口径只差 0–1 个种子，但**少数包差几百个**。
   那少数包才是需要单独看的（`top20_disagreements`）。

**敏感性变体**（评审 A-02 第 5 条）：把种子集合限制为 `closure_complete_strict = true` 的
14,715 个后，
Spearman 为 **0.931**、
Top-20 重合 **19/20** ——
与全量口径**完全相同**。原因是那 277 个"严格不完整"的种子（59 个有图级解析错误 + 218 个
PyPI 明确无依赖）在图里**没有任何闭包记录**，把它们剔除不改变任何统计量。

**为什么必须分开报有符号差与绝对差**：大的**负**差不会进入有符号差的 p95 上尾，
所以"有符号差 p95 = 2"**不能**读成"95% 的节点误差在 ±2 以内"。这里两条都给。

**结论口径**：两个口径在**排序**上高度一致（见 `spearman_within_common_population`），
在**绝对数**上的差异被分解为"叶子截断（漏层）"与"声明层回退边（多边）"两类。
**这不能当作"逐个包的影响面是精确的"的证据。**

更进一步：对任意节点 v，图口径的反向可达集与 `networkx.ancestors(v) ∪ {v}`
**逐个元素完全一致**（抽查 numpy / requests / idna / typing-extensions / tzdata / cattrs 均为 `identical=True`）。
这一步是**实现级**校验，不是数据级校验——它证明位集算法对，不证明数据对。

### 1.4 一个"大小对、成员错"的隐蔽 bug（值得写进报告）

位集打包用 `word[i>>6] |= 1 << (i & 63)`；而 `np.unpackbits()` **默认按 MSB-first
展开每个字节**，会把每个字节内的 8 个位**倒序**输出。后果极其阴险：

* **集合大小（popcount）完全正确** → 「级联规模」这类指标看不出任何异常；
* **集合成员与位置全部错乱**（每个 64 位块内被置换）→
  「加权暴露量」与「按位置取值的布尔掩码」全是错的。

而我们当时的三道防线**都没抓住它**：popcount 与闭包口径吻合（Spearman 0.971）、
曲线形状单调合理、所有数字"看起来很像那么回事"。
最终是拿 `nx.ancestors` 做**集合级**交叉验证才暴露出来。
修法是 `np.unpackbits(..., bitorder="little")`。

**这件事的价值**：它说明"用同一个口径的两个实现互校"是不够的——
当两个实现共享同一个错误的抽象（都只比较 popcount），互校会一致地错。
必须引入**结构不同**的第三方校验（这里是 networkx 的 BFS）。

修复后 `weighted_exposure` 与 `in_degree` 的 Spearman 从 0.821 变为 **0.971**——
这本身就是"原来的值是错的"的又一个证据。

   **不必为"用下载量还是用包数"纠结**，这是本项目一个省事的好消息。

| 包 | 传递依赖者 | 级联深度 | 说明 |
|---|---|---|---|
| typing-extensions | 4,316 | **20** | 又深又广（最危险） |
| attrs / tzdata | 1,690 / 1,729 | **20** | 广且极深 |
| idna / certifi / urllib3 | 3,000–3,900 | 11 | 极广但中等深 |

"深而窄"的包（如 AWS CDK 栈）在一次级联里会**跨很多层**但只波及少数包；
"广而浅"的包（如 idna）一次就波及上千个包但很快止住。
**这是两种不同的失效模式，治理手段也不同**（前者要打断链条，后者要隔离枢纽）。

### 2.4 三个具体案例：漏洞具体怎么"一路传上去"（评审 C-04 第 4 条）

前面全是分布和分位数，它们能说明"影响面重尾"，但说不清**一条链长什么样**。

| 边缘/应用包 | 传递依赖者数排名 500–2000 中下载量最高者 |

1. **同一条链上每一跳的"边"都是可核对的**——`t12_case_paths.csv` 的 `edge_meaning` 列

## 3. 瓶颈识别：哪个指标说了算（RQ2）→ 支持 H2

### 3.1 指标一致性（图 4）

|  | 入度 | 传递依赖者 | 级联深度 | PageRank(重要性) | PageRank(风险继承) | 介数 | k-core | 加权暴露 |
|---|---|---|---|---|---|---|---|---|
| **入度** | 1.00 | 0.96 | 0.96 | 0.97 | −0.08 | 0.61 | 0.39 | 0.97 |
| **传递依赖者** | 0.96 | 1.00 | 0.96 | 0.95 | −0.10 | 0.58 | 0.35 | 0.96 |
| **级联深度** | 0.96 | 0.96 | 1.00 | 0.95 | −0.10 | 0.58 | 0.35 | 0.97 |
| **PageRank(重要性)** | 0.97 | 0.95 | 0.95 | 1.00 | −0.09 | 0.60 | 0.35 | 0.96 |
| **PageRank(风险继承)** | −0.08 | −0.10 | −0.10 | −0.09 | 1.00 | 0.35 | 0.67 | −0.09 |
| **介数** | 0.61 | 0.58 | 0.58 | 0.60 | 0.35 | 1.00 | 0.46 | 0.59 |
| **k-core** | 0.39 | 0.35 | 0.35 | 0.35 | 0.67 | 0.46 | 1.00 | 0.36 |
| **加权暴露** | 0.97 | 0.96 | 0.97 | 0.96 | −0.09 | 0.59 | 0.36 | 1.00 |

三点读数：

1. **入度、传递依赖者数、级联深度、PageRank(重要性)、加权暴露五者互相 ρ ≥ 0.94**，
   在排序意义上**高度冗余**。用其中任何一个都差不多，**贵的那个不划算**。
2. **介数中心性与它们只 ρ ≈ 0.58**——明显低于其余五者之间的 0.94+。
   注意这里的介数是**精确全源介数**（`config: betweenness_k=0`，本图约 60 s），
   不是抽样近似；抽样近似会让这个数字更低更不稳（见 §7 与 `t27`）。原因见 §3.2。
3. **PageRank(风险继承) 与所有瓶颈指标都 ≈ 0 或负**（ρ 在 −0.11 到 −0.08 之间）：
   它度量的是完全不同的东西（"我这个包有多依赖别人"），是**脆弱性**而非**关键性**。
   方向搞反会把结论整个说反。

### 3.2 介数中心性在这个网络里基本失效

介数榜的头部是少数**长链**上的节点（AWS CDK / airflow 那一串），
它们的入度与广度都不大；而广度最大的那些包（`typing-extensions`、
`idna`、`certifi`）介数**恰好是 0**。

原因：本网络的依赖深度极浅（p50 = 2），绝大多数"最短依赖路径"长度为 1–2，
**几乎没有路径会"经过"第三个节点**。广度大的包通常是被"直接依赖"的，
它根本不在任何最短路上。所以介数识别的是"长链上的过路点"，**不是"影响面大"**。

**H2 判定：成立**（事先声明的证伪条件是"介数与真实影响面的 ρ 与传递依赖者数相当，差 < 0.05"；
实测两者差 **0.33**，在"真的有人受影响"的子集上差 **0.50**）。

## 4. 三个口径之间的差额到底意味着什么（RQ3）→ 部分支持 H3

> **本节是全文最容易读错的地方，先立三条规矩**
>
> 1. **每个百分比都写出分母**。S→F 的分母是 **S**，F→V 的分母是 **F**。
>    这两个数不能互换、不能相乘当"总收缩"、更不能混着说。
> 2. **108.7× 是两个口径之间的倍数**，不是"真实世界风险被高估 108.7 倍"。
> 3. **F→V 是口径收缩，不是因果归因**。我们只有当期快照，**没有时间序列**，
>    因此**无法观察"谁在何时升级"**，也就不能把它读成"依赖者完成了 98.98% 的升级"。

### 4.1 三级数字（图 5）

| 口径 | 定义 | 命中 (包, 漏洞) 对 | 相对 S 的保留比例 |
|---|---|---|---|
| **S 结构上界** | 任何传递依赖者都算受影响（无视版本） | **1,188,370** | 100% |
| **F 反事实：漏洞至今未修复** | 把区间改成 `[introduced, ∞)` | **1,075,784** | **90.49%** |
| **V 现实：OSV 区间 + 当期解析版本** | 依赖者的解析版本落在脆弱区间内 | **10,931** | **0.92%** |

* **S / V = 108.7×**（加权下载量口径 **367.6×**）——**模型内部**的倍数
* **S / F = 1.10**，**F / V = 98.4**
* **S → F**：(S−F)/S = **9.47%**（分母 S）
* **F → V**：(F−V)/F = **98.98%**（分母 F）
* 逐 advisory 看：**86.2%** 的 advisory 在当期解析结果里**一个人都不影响**
* 过近似倍数分布（有真实影响的 1,326 条）：中位数 **31.4×**，p90 **250×**，22.3% 超过 **100×**
* (包, 漏洞) 对层面：153,909 个结构对 vs 1,917 个现实对 → **80.3×**

### 4.2 两个收缩率各自在说什么（一张表说清，且**不**做因果归因）

| 收缩 | 公式 | 分母 | 这一步**只**改动了什么 | **不能**说什么 |
|---|---|---|---|---|
| S → F | (S−F)/S = **9.47%** | **S** | 只抹掉 OSV 的 `fixed` 边界。收缩很小 ⇒ 绝大多数结构命中本来就落在 `≥introduced` 一侧 | 不能说"依赖者升级了 9.47%"——S 口径里根本没有 fixed 这个概念，也就没有"升级"这个动作 |
| F → V | (F−V)/F = **98.98%** | **F** | 把命中集合从「`≥introduced`」收缩到「落在脆弱区间内」 | 不能说"补丁发布止血解释了 98.98%"——这需要时间序列，我们没有 |

**F→V 其实是一条可以逐条核对的恒等式，不是一个发现。**
在一个"单一 `[introduced, fixed)` 区间"的 advisory 上，

```
F 命中 ∖ V 命中  ≡  { 依赖者 : resolved_version ≥ fixed }
```

我们把这条恒等式**真的算了一遍**（`t22_summary.json` 的
`n_single_range_advisories_checked` / `n_ge_fixed_single_range_count` /
`shrink_F_to_V_from_closed_advisories` / `shrink_F_to_V_from_open_advisories`）：

* `shrink_F_to_V_from_open_advisories` 应该为 **0**（区间未封口时 F 与 V 的定义重合）——
  这是口径自洽的自检；
* `shrink_F_to_V_from_closed_advisories` 应与 F−V 一致；
* 单区间 advisory 上的 "`≥ fixed`" 计数应与上面那个差集吻合。

### 4.3 **唯一**能把"结构扫描准不准"讲清楚的地方：25 条至今没补丁的 advisory

那 25 条**至今没有补丁**（区间未封口）的 advisory，结构口径与现实口径的比值只有 **1.23×**。
也就是说：

> **当漏洞真的还没被修的时候，简单的结构扫描是准的；
> 它的错，恰恰错在把"已修的历史存量"当成了"当前风险"。**

这一条是本节唯一带机制含义的结论，而且它不依赖任何因果假设——
它只是比较"有补丁的 advisory"与"没补丁的 advisory"这两组的结构/现实比值。

### 4.4 机制描述（只描述可观测量，不推断原因）

对 9,186 条带固定修复版本的 advisory：**依赖者的解析版本落在 `fixed` 之后的比例**，
中位数 = 1.000，均值 = 0.980。

这里**只**陈述一个可观测量：*在当期解析结果里，绝大多数下游依赖者的版本已经 ≥ `fixed`。*
我们**不**据此推断"它们是被升级上去的"——没有历史版本快照，这个推断做不了。

### 4.5 榜单对照（这个对照本身就是结论）

**按结构口径最吓人的 Top 6**：

## 5. 韧性：修复 vs 移除，以及"与门 vs 或门"（RQ4）→ 支持 H4

### 5.1 半衰阈值：S(q) 掉到 0.5 需要的移除比例（越小越脆弱）

| 移除策略 | **AND 规则**（软件真实语义） | **OR 规则**（食物网语义） |
|---|---|---|
| 按 PageRank(重要性) | **< 0.5%**（瞬间崩塌） | 3.71% |
| 按入度 | **< 0.5%**（瞬间崩塌） | 3.83% |
| 按传递依赖者 | **< 0.5%**（瞬间崩塌） | 4.74% |
| 按下载量 | **< 0.5%**（瞬间崩塌） | 7.21% |
| 按 k-core | 0.82% | 11.04% |
| 按介数 | **3.73%** | > 30%（在预算内不崩） |
| **随机** | **12.62%** | > 30%（在预算内不崩） |

**H4 判定：成立。** 在 q = 0.5%（79 个包）时：

| 策略 | AND 规则的 S | OR 规则的 S | 差距 |
|---|---|---|---|
| 按传递依赖者 | **0.378** | **0.796** | **41.8 pp** |
| 按入度 | 0.375 | 0.749 | 37.3 pp |
| 随机 | 0.967 ± 0.023 | 0.994 | 2.8 pp |

* 靶向移除时，**两规则差 37–42 个百分点**，远超事先声明的 5 个百分点证伪线。
* 但**随机移除时两规则只差 3.4 个百分点**——这本身是个有意思的观察：
  规则选择的重要性**与攻击的靶向程度正相关**。

把食物网的"次级灭绝"模型直接搬到软件上，会让生态看起来**远比实际稳健**。
原因是结构性的：**软件依赖是"与门"**（缺一个就废），**食物网是"或门"**（还有别的猎物）。

### 5.2 靶向 vs 随机：18.8 倍的差别

q = 0.5%（79 个包）时：

| | 种子包被破坏的比例 |
|---|---|
| 按传递依赖者 / 入度 / PageRank 移除 | **60.5% – 61.8%** |
| 随机移除（30 次，±1 s.d.） | **3.9% ± 2.8%** |

⇒ **精准移除那 78 个瓶颈包，六成的包立刻不可构建；随机移除同样数量，只有 4%。**
破坏率的比值是 **18.8 倍**。

`q_half` 更能说明问题：随机移除需要 **12.62%**（≈2,140 个包）才让 S 掉到 0.5，
而按传递依赖者移除在 **< 0.5%（< 79 个包）** 就已经做到了。

介数是所有"聪明指标"里最差的一个（q=0.5% 时 S 仍有 0.557）。

### 5.3 情景对照：修复 vs 移除（图 10）

| 处理 k 个瓶颈包 | 情景 P「修复」：总暴露量下降 | 情景 R「移除」：总暴露量下降 | 情景 R：种子包不可构建比例 |
|---|---|---|---|
| 1 | 0.0% | 79.6% | **34.0%** |
| 2 | 6.3% | 89.9% | 41.1% |
| 5 | 22.4% | 90.7% | 42.4% |
| 10 | **29.3%** | 96.0% | **52.2%** |
| 20 | 37.2% | 97.7% | 56.0% |
| 50 | 66.3% | 98.7% | 59.6% |
| 500 | 95.1% | 99.9% | 67.7% |

**这是本项目方法论上最要紧的一条**：
情景 R 的"暴露量下降"看起来更漂亮，但**含义完全相反**——
它的下降是因为**暴露者自己已经死了**。只报一个指标会得出"移除比修复更有效"的
反向政策结论。

**正确的读法**：修复 10 个瓶颈包，可以在**零可用性代价**下把生态总暴露量削掉 **29.3%**；
移除同样 10 个包，暴露量虽然掉 **96.0%**，但**一半以上（52.2%）的包都不能用了**。

> **口径修正（评审意见 C-02 / A-02）**：情景 R 的暴露量权重 `exposure_remove` 现在用**动态宽度**
> ——只数当时**还活着**的传递依赖者（`|reverse_reach(p) ∩ alive|`，位集一次 popcount），
> 而不是原始图上的静态宽度 `n_transitive_dependents`；
> **并且情景 P 与情景 R 现在用同一个宽度定义**（都是图口径），
> 所以在 k=0 时两列**恒等**（脚本里有断言：不相等直接退出）。
> 旧口径保留为 `exposure_remove_static`，用来量化这次修正改了多少：
> 在 k=0 时它与新口径差 **11.3%**，
> 这个差就是"闭包口径 vs 图口径"的宽度差。
> 修正是让 R 的暴露量**更小**，因此它**加强**而不是推翻"R 的下降是因为暴露者自己死了"这个读法。

### 5.4 第三种治理动作：**保护**（评审意见 C-03）

题面写的是"关键包被修复 **或** 被移除"，前两个动作就是上面的情景 P 与 R。
但课程分工里还写了"保护"，而"保护"在依赖网络上有**独立含义**：

| 动作 | 语义 | 在图上发生了什么 |
|---|---|---|
| 修复 patch | 包还在、结构不变，只是它自己不再引入漏洞 | 缩小"漏洞源集合"，结构不动 |
| 移除 remove | 包从注册表消失 | 删点 ⇒ 依赖它的东西全崩 |
| **保护 protect** | 钉版本 / vendor / CI 校验哈希 ⇒ **即使它自己的依赖坏掉，它也不会跟着坏** | **切断级联传播路径**（防火墙节点） |

新增 `src/28_exp_protection.py`。设计上每个对照都排除一种具体替代解释：

* 破坏预算 **q 固定** ⇒ 排除"保护之所以有效只是因为破坏变少了"；
* 保护额度 **k 固定** ⇒ 排除"保护之所以有效只是因为多保护了几个"；
* **`protect_random`**（随机保护同样 k 个）⇒ 排除"任何 k 个包被保护都有这个效果、枢纽排名没用"；
* **`k = 0`** 那一行 ⇒ 排除"这个提升来自模型本身"。

脚本启动时做一次**交叉校验**：保护集为空时，逐点 BFS 传播的结果必须与实验四的位集并集
**逐位相同**，否则直接退出（不产出错误结果）。结果见 `t28_protection_*.csv`，
一致性校验见 `t28_protection_check.json` 的 `cross_check_vs_bitset`。

**实测结果**（ΔS = 相对"不保护"基线的存活种子比例提升；每格是 `保护枢纽 / 随机保护`）：

| 破坏模式 | q | 不保护的 S | k=10 | k=50 | k=200 | k=500 |
|---|---|---|---|---|---|---|
| 靶向 | 1% | 0.351 | +0.091 / +0.000 | +0.205 / +0.003 | +0.454 / +0.011 | +0.649 / +0.024 |
| 随机 | 1% | 0.905 | +0.011 / +0.000 | +0.033 / +0.000 | +0.057 / +0.002 | +0.069 / +0.007 |
| 靶向 | 10% | 0.280 | +0.061 / +0.000 | +0.121 / +0.003 | +0.241 / +0.011 | +0.368 / +0.027 |
| 随机 | 10% | 0.536 | +0.081 / +0.000 | +0.124 / +0.002 | +0.211 / +0.008 | +0.269 / +0.022 |

* 同一 k 下"保护枢纽"的 ΔS 是"随机保护"的 **48.5 倍**（中位数；最小 9.6 倍，最大 452.7 倍）；
* 最极端的一格：靶向破坏 q=1% 且保护 Top-500 时，ΔS = **+0.649**，
  而随机保护 500 个包的 ΔS 只有 **+0.0244**；
* **结论**：保护预算花在**枢纽包**上杠杆极大；花在随机包上接近白花钱。

## 6. 对照实验：这个生态"特殊"在哪（排除替代解释）

### 6.1 保度序列零模型：**两族 × 两口径**的分解（图 8）

做法：有向双边交换，精确保持每个节点的入度与出度，只随机化"谁连谁"。
两个族各 **20 次实现**，度序列由脚本内 ssert 逐点校验（不成立立刻退出）：
朴素族 degree（约 7 次成功交换/边，成功率 87%）与保环族 cycle_pres（6.3 次/边，成功率 78%，
另有 37,101 次因"新边会向后"被拒）。

> **★ 这一节推翻了本项目上一版的一条主要结论（评审意见 D-01）。**
>
> 上一版只跑了朴素保度交换，得到"平均级联规模从 11 涨到 500 上下，约 38–57 倍"
> 并据此说"保护生态的是它的分层结构"。评审问了一句：**随机图自己长出来的大环算不算数？**
> 我们去测了——不算数的地方比想的多。

**第一步：确认伪影存在。**

| | 真实图 | 朴素族 degree | 保环族 cycle_pres |
|---|---|---|---|
| 最大强连通分量（20 次实现的中位数） | **8** 个节点 | **484** 个节点 | **2** 个节点 |
| 非平凡 SCC 个数 | 20 | 约 1.5 | 约 2 |
| 落在非平凡 SCC 里的节点占比 | **0.33%** | 约 2.9% | 可忽略 |

真实依赖图几乎没有环（0.33% 节点），而朴素双边交换能造出**中位数 484 个节点**的巨型 SCC。
一个 484 节点的 SCC 意味着它每个成员都能"反向到达"另外 459 个成员 ——
这会**纯靠人造的环**把零模型的反向可达集抬起来。

**第二步：用保环零模型把这一项剥掉。**

保环族的做法：按真实图凝缩拓扑序给每个节点一个全局序键；交换后两条新边都必须"序键向前"；
把原本在 SCC 内部（可能向后）的 **39 条边冻结**不参与交换。
结果是最大 SCC 中位数压到 **2**，度序列仍然精确保持。

**第三步：分解。**

| 口径（node = 反向可达的节点数） | 均值 | 相对真实网络 |
|---|---|---|
| **真实网络** | **11.08** | 1.00× |
| 保环族 cycle_pres（形貌随机化，无环性保留） | **20.53 ± 1.53** | **1.85×** |
| 朴素族 degree（形貌随机化，无环性丢失） | **526.92 ± 94.85** | **47.6×** |

于是那个"47.6 倍"可以干净地拆成两段：

`
真实 → 朴素族      47.6×   其中 ................ 真实拓扑 + 巨型环伪影
真实 → 保环族      1.85×   ← **真实拓扑本身的贡献**
保环族 → 朴素族    25.7×   ← **纯人造环的贡献**
`

**结论必须改写**：真实 PyPI 依赖网的分层结构确实让级联规模比"同样度序列、但不分层"的
随机图小一些，但只是 **1.85 倍**这个量级，**不是上一版说的"一个半到两个数量级"**。
上一版那个数字里有约 96% 是人造环的贡献。

**第四步：连带撤回第二条结论。**

上一版还说"随机移除 q=1% 时真实网络 S=0.920、零模型 S=0.518±0.042 ⇒ 真实生态对随机故障的
鲁棒性是同度序列随机网络的近 6 倍"。用保环族重算：

| 随机移除 | 真实网络 | 保环族 cycle_pres | 朴素族 degree |
|---|---|---|---|
| q = 0.5% | **0.9611** | 0.9235 ± 0.0799 | 0.5383 ± 0.0931 |
| q = 1% | **0.9201** | 0.8865 ± 0.1050 | 0.5143 ± 0.0391 |
| q = 5% | **0.7029** | 0.5964 ± 0.0915 | 0.4716 ± 0.0298 |

⇒ 真实网络对随机故障的鲁棒性只比"同度序列、保留无环性"的随机图高 **3–18 个百分点**，
**"近 6 倍"这个结论撤回**。它同样是巨型 SCC 造成的。

**什么仍然成立？**

* **排名几乎不变**：真实网络与零模型之间反向可达规模的 Spearman 在
  保环族下是 **0.980**、朴素族下是 **0.959**。也就是说：
  *谁是枢纽由度序列决定*，这一点不受环伪影影响，结论稳健。
* **靶向移除下三者几乎重合**：q=0.5% 按入度移除，真实 **0.3751**、
  保环族 **0.3475**、朴素族 **0.3512**。这个"谁都救不了你"的结论不变（见 §6.2）。
* 分布形状的重尾性与 Gini 也基本不变。

**这一节的判据是事先写定的**：任一结论若只在朴素族成立、在保环族或凝缩口径下消失，
就当作环伪影撤回。上面三条里前两条按这个判据被撤回，第三条保留。
完整数字见

### 6.2 靶向移除下三者几乎一样（这是唯一没被推翻的那一半）

| q（按入度移除） | 真实网络 | 保环族 `cycle_pres` | 朴素族 `degree` |
|---|---|---|---|
| 0.5% | **0.3751** | 0.3475 ± 0.0010 | 0.3512 ± 0.0021 |
| 5% | **0.3246** | 0.3137 ± 0.0007 | 0.3139 ± 0.0008 |
| 30% | **0.2267** | 0.2260 ± 0.0003 | 0.2258 ± 0.0003 |

**解读**：如果攻击者知道该打谁，**度序列就足够决定结果**，拓扑的"分层结构"救不了你。
注意这个结论在**两族零模型下都成立**（差值 ≤ 0.03，且随 q 增大继续收敛），
所以它不属于环伪影，可以保留。

这给出一个政策含义：**防御的价值不在"祈祷没人盯上枢纽"，
而在"别让枢纽变成单点"** —— 这与 §5.4 的保护情景是同一个意思。

### 6.4 时间分组关联（把结构固定在当前快照，把事件按年份切两段）

> 评审意见 B-05：这**不是**"用历史网络预测未来"。我们只有一份当期网络，
> 所以它只是**分组关联**——同一组结构指标在早/晚两个披露分组上的秩相关是否相近。

| 切分年 T | 早期（≤T）advisory 的 ρ（传递依赖者数） | 晚期（>T）advisory 的 ρ |
|---|---|---|
| 2018 | -0.096（n=314） | 0.359（n=7,375） |
| 2019 | -0.091（n=538） | 0.374（n=7,151） |
| 2020 | -0.062（n=996） | 0.387（n=6,693） |
| 2021 | +0.003（n=3,164） | 0.405（n=4,525） |
| 2022 | +0.072（n=4,984） | 0.427（n=2,705） |
| 2023 | +0.124（n=5,424） | 0.477（n=2,265） |

**早期分组 ρ 接近 0（甚至为负），晚期分组 ρ 稳定在 0.36–0.48。**

这个结果**不是**"结论不稳"，而是**同一个机制的又一次显现**：
早期 advisory 几乎全部已被修复，其"现实影响"恒为 0，于是任何结构指标与它的秩相关自然趋于 0；
越晚的 advisory，"未消化"的比例越高，排序能力就越明显（0.33 → 0.48 单调上升）。

**诚实结论**：拓扑瓶颈分数的排序能力**与 advisory 的时间分组强烈耦合**。
它排序的是"**仍然活着的**风险"，不是"历史储量"，更不是"未来风险"。
必须在报告里写清这条，否则会被误用成"预测所有漏洞影响"的工具。

## 7. 敏感性：排序协议（固定 / 分阶段重算 / 严格逐点重算）

> **先纠正一个我们写错过的断言（评审意见 B-02，P0）**
>
> 早期版本在 `src/26_exp_adaptive.py` 文件头写过：
> "删除其他节点不改变入度，所以固定与自适应在数学上等价"。
> **这是错的。** 图里 `u→v` 表示 u 依赖 v，所以删掉 u 就删掉了边 `u→v`，
> **v 的入度减 1**。两节点反例：`A→B, C→B` 时 `in_degree(B)=2`，删掉 A 后变成 1。
> 脚本启动时会跑这个自检，不成立就直接退出。
>
> 正确说法只能是："**在本节采用的协议粒度与本样本上，观察到的差异是……**"。

本节比较 **5 种协议**：

| 协议 | 含义 |
|---|---|
| `fixed` | 只在原始网络上排一次序 |
| `adaptive_staged` | 每跨过一个 q 档，在剩余图上重排一次（本项目原来的做法） |
| `adaptive_staged_with_cascade` | 同上，但**级联失效的包也从排名图里删掉** |
| `adaptive_per_node` | **严格逐点**：每删除一个包就重排一次（仅对入度实现，见下） |
| `adaptive_per_node_with_cascade` | 同上，且级联失效的包也移除 |

`adaptive_per_node` 用**增量维护**实现（删 u 时只把 u 的后继的入度计数减 1，总代价 O(E)），
所以真的跑得动。其余指标（PageRank / 介数）每删一个包就要重算，成本不可接受，
**因此逐点协议只对入度实现——这一点写在 `t26_protocol_check.json` 里，不假装已做。**

实测（完整数字见 `t26_adaptive_pivot.csv`）：

| 策略 | 固定 vs 分阶段 | 固定 vs 分阶段+级联 | 固定 vs 严格逐点 |
|---|---|---|---|
| 按入度 | 差异见 `t26_adaptive_pivot.csv` | 同上 | 同上 |
| 按 PageRank(重要性) | 同上 | 同上 | **未实现**（成本不可接受） |
| 按介数 | 同上 | 同上 | **未实现** |

**入度排名几乎不动，但这回我们有测量出来的原因，而不是一句错误推导**：

* 瓶颈榜前 79 名的**平均出度只有约 1.9**，其中 38 个出度为 0；
* 删掉它们只触碰全部 47,944 条边里的大约 **151 条**（0.3%）；
* 于是入度排名的整体形状几乎不动（Top-79 重合 78/79，全局 Spearman 0.9998）。

⇒ 结论：**对本文推荐的口径（入度 / 传递依赖者数），排序协议不是问题；
但对介数这种局部结构指标，必须声明协议，否则结果不可比。**

**介数确实会因协议而变**（q=5% 时的差异是所有策略里最大的）——因为介数的"桥梁"身份
在移除后确实会转移。这也是为什么正文不把介数当作主瓶颈分数。

## 8. 假设检验汇总

| 假设 | 事先声明的证伪条件 | 实测 | 判定 |
|---|---|---|---|
| **H1** 级联影响面重尾、暴露高度集中 | 前 1% 承担 < 50% | 前 1% 承担 **64.6%**（加权 83.8%） | 成立 |
| **H2** 拓扑中心性 ≠ 级联影响面；传递依赖者/PageRank 优于度与介数 | 介数与真实影响面 ρ 与传递依赖者数差 < 0.05 | 差 **0.29**（0.052 vs 0.386）；严格子集下介数为 **−0.067** | 成立 |
| **H3** 结构口径系统性高估 | 过近似中位数 < 1.5 | 中位数 **31.4×** | 成立 |
| **H3′**（事后追加）高估可归因于"依赖者已越过修复版本" | 这条**不能**被证伪，因为它不是可检验命题 | 只能验证恒等式：F∖V ≡ `resolved ≥ fixed` | **降级为口径描述，不作为机制结论** |
| **H4** 韧性强烈依赖失效规则，AND 崩塌远早于 OR | q ≤ 0.1 区间两规则差 < 5 个百分点 | q=0.5% 时按传递依赖者移除差 **41.8 个百分点** | 成立 |
| **H5**（本轮新增）「分层结构」让级联规模显著小于同度序列随机图 | 保环零模型下差距 < 1.5 倍则视为无实质效应 | 保环族只差 **1.85 倍**；朴素族的 45.6 倍里有约 96% 是人造环 | **上一版结论撤回，改写为「1.85 倍量级的有限效应」** |
| **H6**（本轮新增）真实网络对随机故障更鲁棒 | 保环零模型下 S(q) 差 < 5 个百分点则视为无实质效应 | q=1% 时 0.920 vs 0.871±0.105（差 4.9 pp） | **上一版「近 6 倍」结论撤回** |

**关于 H3 的诚实说明**：我们原来把 H3 写成"机制是依赖者已越过修复版本"。
这条**不可证伪**——它既不能被数据推翻，也不能被数据支持，因为我们没有时间序列。
现在把它降级成 §4.2 的**口径描述**（一条可逐条核对的恒等式），
H3 只保留"结构口径系统性高估"这个可测的命题。

**三个必须写在结论旁边的限定**：

1. 所有"影响面"都是**上界**。我们没做方法级可达性分析，
   版本脆弱 ≠ 代码真的调用了脆弱函数。
2. 现实口径衡量的是**"今天全新解析（fresh install）"**，
   不是"所有已部署环境"。大量用户仍 pin 在旧版本上，那部分存量风险不在本口径里。
   **我们也没有时间序列，无法观察升级行为。**
3. 拓扑指标的**同时性排序能力**只有 ρ ≈ 0.4，且随 advisory 的时间分组强烈变化（§6.4）。
   它不是"漏洞风险预测器"，而是"仍然活着的风险的排序器"。
