## 1. 数据源（三个，全部公开、无需密钥）

| 数据源 | 用途 | 原始文件 | 抓取规模 |
|---|---|---|---|
| **PyPI 月下载量榜**（hugovk 镜像 pypistats 的 ClickHouse 统计） | ① 研究对象边界（前 N 名）② 使用量权重 | `data/raw/top-pypi-packages.min.json` | 15,000 行，`last_update = 2026-11-01` |
| **deps.dev v3 API**（Google osv-scanner 团队） | 每个包的**已解析依赖闭包**，含每个依赖的解析版本号 | `data/raw/depsdev_deps.jsonl` | 14,992 个包，166,705 条闭包记录 |
| **OSV.dev PyPI 打包漏洞库** | 漏洞的版本影响区间（`introduced / fixed / last_affected`） | `data/raw/osv_pypi_all.zip` | 26,810 条 advisory，31,957 条 (advisory, 包) 记录，覆盖 13,695 个包 |

**为什么不用 PyPI 的 `requires_dist` 直接建图？**
PyPI 元数据写的是 PEP 508 的**约束表达式**（`urllib3>=1.21.1,<3`），不是解析结果。
直接用它建图有三个问题：条件依赖（`; extra == 'test'`、`; python_version<'3.8'`）、
同一生态内不同包的版本需求互相冲突（版本求解）、以及最关键的——**我们无法知道
"某个包实际会装到哪个版本"，于是无法做版本感知的级联判定**。
deps.dev 返回的是**一个具体版本**的已完成解析闭包，节点带 `DIRECT/INDIRECT`
关系与解析后的确切版本号，正好补上这一环。

**覆盖率与失败记账**（不静默丢弃任何东西）：

> **口径修正（评审意见 A-01）**：早期版本把 `deps_status=ok` 直接当成"闭包完整"。
> 这是过度声称——deps.dev **返回了一个对象**，不等于它解析成功，也不等于解析结果无错。
> 现在分三层记账：**已解析 / 严格完整 / 只有声明层回退**，
> 并把 deps.dev 返回的**图级 `error`** 与**节点级 `errors` 原文**都保留下来。
> 具体数字见 `data/processed/graph_stats.json` 的
> `seeds_resolved_ok` / `seeds_strict_complete` / `seeds_with_graph_error` /
> `node_level_errors_total` / `fallback_*`。

| 记账项 | 含义 | 处理 |
|---|---|---|
| `seeds_resolved_ok` | deps.dev 给出了已解析闭包 | 主口径 |
| `seeds_strict_complete` | **已解析 且 图级无错 且 无节点级错误** | 敏感性分析用的严格子集（`src/11`） |
| `seeds_with_graph_error` | deps.dev 明确返回了解析失败原因（如 `resolution impossible`、`context deadline exceeded`） | 该种子的传递闭包视为**截断**，不当完整 |
| `node_level_errors_total` | 闭包里逐节点的 `errors` 条数 | 同上 |
| `seeds_unresolved_fallback` + `fallback_ok` | deps.dev 无解析结果（404），回退到 PyPI `requires_dist` 且**成功** | 闭包**只有一层**，广度统计会**低估**，单独记账 |
| `fallback_no_requires_dist` | 回退成功、但 PyPI **明确没有声明任何依赖** | 这是真的"无依赖" |
| `fallback_fetch_failed` | 回退时 PyPI 请求失败 | **绝不**当成"无依赖"；可用 `python src/02_fetch_deps.py --refetch-weak` 重抓 |
| 包在 deps.dev 上不存在 | 已删除 / 测试夹具（如 `piot-fixture-*`、`aaaaaaaaa`） | 从图中缺席，不参与任何统计；清单在 `data/raw/depsdev_failed.jsonl` |

**三个会让"看起来没问题"的错误，我们各加了一道闸**：

1. **抓取失败 ≠ 没有依赖**。两者在数据里都表现为"空的依赖列表"。
   所以回退源额外记一个 `fallback_status ∈ {ok, no_requires_dist, fetch_failed}`。
2. **重抓会追加**。`--refetch-weak` 把弱记录剔出后重抓，于是 JSONL 里同名记录可能出现两次。
   建图时按 `name` **去重保留最后一条**，并把去重条数记进 `graph_stats.json`。
3. **并发打 pypi.org 会被 429**，而旧的 `_get_json` 会静默返回 `None`——
   又变成"抓取失败伪装成没有依赖"。现在回退路径走同一个限速器并重试 4 次。

## 2. 时间切片的定义（把"固定切片"变成可审计的事实）

依赖关系是动态的，题目也点出了这个难点。本项目的切片定义为：

```
时间切片 ≡ ( 下载量榜的统计月份 , 每个包被解析到的具体版本号 )
```

* 下载量榜自带 `last_update`（本项目为 `2026-11-01`），写入 `universe.csv` 每行；
* **每个包被解析到的确切版本号逐包落盘**（`universe_coverage.csv` 的 `resolved_version`；
  `closures.parquet` 里每个依赖的 `dep_version`）。

因此这一张网可以在任何时候用同一批版本号重建，不依赖"抓取那天"的服务器状态。
这是把"依赖是动态的"这一难点处理成可检验事实的关键一步。

## 3. 网络模型

### 3.1 节点

```
N = S ∪ T
S = 下载量榜前 15,000 名（有 7 个在 deps.dev 上不存在，实际 14,992）
T = 出现在种子闭包里但不在榜上的包（本项目仅 788 个）
```

`T` 只占 4.6%，说明**榜内 15,000 个包已经互相闭合了 99.5% 的依赖闭包**
（`frac_closure_nodes_in_universe = 0.9947`）。这是个好消息：我们的截断偏差很小，
但它仍然被量化并报告（见 §5）。

### 3.2 边

```
边 (u → v) 存在 ⟺ 包 u 的直接依赖声明里包含包 v
```

* **方向 = 依赖流方向**（u 依赖 v）。因此 `in_degree(v)` = **直接依赖 v 的包数**、
  `out_degree(v)` = **v 直接依赖的包数**，不能反过来（评审意见 B-04）。
* **级联传播方向相反**：v 出问题 → 沿 v → u 传播。报告里每次说"上游/下游"都会显式标注。
* **只保留直接边**。deps.dev 的闭包同时给出 `DIRECT` 与 `INDIRECT`；
  如果把 `INDIRECT` 也当作边，图会退化成近团状，所有中心性指标被压平。
* **回退边单独标记**：来自 PyPI `requires_dist` 的边记为 `rel = DIRECT_DECLARED`，
  它们的语义是"**声明了**依赖"而不是"**解析到**依赖"，因此所有用到边的实验都单独核对这一类
  （见 `src/29` 的 `S3_declared_fallback` 分层）。
* **回退边的 marker 在显式固定的基准环境里求值**（评审意见 A-03）：
  `python_version=3.11 / python_full_version=3.11.9 / os_name=posix / sys_platform=linux /
  platform_machine=x86_64 / platform_python_implementation=CPython / extra=""`，
  写在 `config/config.yaml` 的 `experiments.fallback_marker_environment`。
  用 `Requirement(spec).marker.evaluate(environment=env)` **真值求值**，
  而不是看字符串里有没有 `extra`。换环境会得到略不同的边集，这一点必须声明。
* **自环剔除**：在**一个阶段**完成（建边时 `if nm == seed: continue`）。
  早期版本另有一个 `graph.drop_self_loops` 配置开关，但那时边已经被删掉了，
  **那个开关无论设什么都无效**，已删除（评审意见 A-04）。
* **榜外叶子是"未扩展边界"**：`nodes.csv` 的 `expansion` 列取值
  `seed_expanded` / `boundary_not_expanded`。我们没有抓它们的出边，
  所以**不能**把它们当成"没有依赖"（评审意见 A-04）。

### 3.3 权重

* 节点权重 = 该包的月下载量；榜外包无数据，**显式置为缺失而不是 0**，
  在加权指标里排除（不臆造）。
* **边不加权**：deps.dev 不提供"用了多少"的信息。我们不臆造权重，
  并在局限性里说明这会**高估**弱依赖的影响。

### 3.4 简化假设清单（必须显式声明）

| 简化 | 处理 | 偏差方向 |
|---|---|---|
| 依赖强度 | 不加权 | 高估弱依赖的影响 |
| 可选依赖 | 剔除 `extra == ...` 的条件依赖 | 低估"装了某 extra 才触发"的漏洞 |
| 版本 | 用**已解析的具体版本**，不是声明区间 | 是"解析器的选择"，不是"每个用户实际装的" |
| 多版本共存 | 一个包一个节点 | 可能引入实际闭包里不存在的路径；已用**同总体集合比对**量化（`src/11`） |
| 方法级可达性 | **不做到** | 版本脆弱 ≠ 代码真调用，我们的"现实影响"仍是**上界** |
| 时间 | 单层静态快照 | 结论只对该切片成立；**没有时间序列 ⇒ 无法观察升级行为** |
| 环 | 允许（实测 20 个 SCC，最大 8 个节点） | 来自条件依赖互相引用；用 SCC 凝缩做精确处理，同 SCC 成员共享深度 |

### 3.5 三种失效规则的**边界**（评审意见 C-04）

| 规则 | 它能说什么 | 它**不能**说什么 |
|---|---|---|
| **R_AND** | 任一**必需**直接依赖不可用 ⇒ 包不可用 | 这只是对"构建/可用性"的**简化模型**。可选依赖、替代实现（如 `pyOpenSSL` vs 标准库 `ssl`）、运行期才走的分支都**不满足**这个假设 |
| **R_OR** | 全部直接依赖不可用 ⇒ 包不可用 | 它来自食物网的"次级灭绝"，用来展示**规则敏感性**，**不是** PyPI 的安装机制。我们只用它做对照，不用它下任何政策结论 |
| **R_VULN** | 传递闭包里存在受影响包 ⇒ 包受影响 | 是**上界**：不含方法级可达性 |

**广度与深度的口径**：

* `n_transitive_dependents` / `n_transitive_all_nodes` / `weighted_exposure`
  三者**都不含源节点自身**（"受影响的其他节点/种子数"）。
  位集实现里显式做 `mask.sum() - 1`（`src/21_exp_cascade.py` 的 `reverse_reach`）。
* `cascade_depth` 定义为**凝缩图**上的最长反向路径跳数。有环时同一 SCC 内所有成员共享深度，
  SCC 内部不再区分（20 个非平凡 SCC、最大 8 个节点、占 0.33% 节点）。

**单点失效的 3 个具体案例**（`src/12_cascade_cases.py`）：基础依赖包 / 中间库 / 边缘应用包，
每类按**事先声明的规则**挑选（不是挑好看的），输出按跳数分层的扩散、
以及 3 条**逐跳可核对**的依赖链（`results/tables/t12_case_paths.csv` 的 `edge_meaning` 列
直接写着"X 直接依赖 Y"，可在 `edges.csv` 里逐条核对）。

## 4. 三种级联规则（题目要求"传播规则需要自己定义"）

| 规则 | 定义 | 现实对应 | 用途 |
|---|---|---|---|
| **R_AND（合取）** | 包的**任一**直接依赖不可用 ⇒ 包不可用 | **软件的真实语义**：缺一个依赖就 build 失败 | 主口径；失败集合 = 被移除集合的反向可达并集 |
| **R_OR（析取）** | 包的**全部**直接依赖不可用 ⇒ 包不可用 | **食物网的次级灭绝语义**：捕食者失去全部猎物才灭绝 | 对照；用"存活依赖计数 + 队列"迭代求解，O(V+E) |
| **R_VULN（漏洞）** | 包的传递闭包里存在受影响的包 ⇒ 包受影响 | 依赖扫描 | 分三级口径（结构 / 反事实 / 现实），见 §6.3 |

**这是本项目的核心论点之一**：把食物网的级联模型直接搬到软件上会
**系统性低估**软件生态的脆弱性，因为软件是"与门"而非"或门"。
在 §6.4 里这个差异被量化成了 40 个百分点的 S(q) 差距。

### 5.1 一个真实踩过的数据清洗坑（值得写进报告）

PyPI 上**真的存在**名为 `nan`、`null`、`none` 的包。pandas 的默认 NA 规则
（`keep_default_na=True`）会把 `null` / `none` / `nan` 读成缺失值 `NaN`。
后果非常隐蔽：

1. 这个包从图里**静默消失**，不报错、不影响任何指标"长相"；
2. 更糟的是，我们在第一版里把一个包名变成了 `float('nan')` 送进 API，
   **deps.dev 居然真的解析到了一个叫 `nan` 的包**，于是数据里多了一条假记录。

修复方式是全局 `keep_default_na=False, na_values=[""]`，并把 `nan/null/none`
三个包补抓回来。这正是题目所说"数据清洗比交通/金融数据更琐碎"的一个具体样本。

### 5.2 第二个坑：零模型的边顺序导致"不完全可复现"

双边交换的起点是一个 `set[tuple[str, str]]`。Python 的字符串哈希在每个进程里
加盐随机化，因此 `list(some_set)` 的顺序**跨进程不稳定**。后果是：同一 random seed、
同一份数据，在不同进程里跑出的零模型结果会相差约 **0.02%**——不报错、不影响定性结论，
但违反"逐位可复现"。

修法两处：

1. `randomize_edges()` 里先 `sorted(edges)` 建立确定性的初始边列表；
2. `run_all.ps1` 里固定 `PYTHONHASHSEED=0`。

修完后两次独立运行结果**逐位相同**（实测 `null_mean` 三次实现为 564.27 / 627.01 / 424.67，
两次运行完全一致）。这一点是本项目"材料可复现"这一项的实测证据，而不是声明。

### 5.3 第三个坑：`set` 迭代顺序也影响观察本身

本项目还踩过一个更隐蔽的同类问题：`nx.pagerank(G.reverse())` 方向搞反会得到
"风险继承"而不是"瓶颈重要性"（两者在本数据上 Spearman −0.065，几乎正交）。
这类错误不会报错、指标看起来也"像那么回事"，只能靠**语义自查**发现。
我们因此把两个量分开命名并写进 README 的口径表，避免后人也踩。

## 6. 实验设计与实现要点

### 6.1 实验二：指标计算（`src/21_exp_cascade.py`）

* **精确广度**：用 deps.dev 的已解析闭包直接统计"被多少种子包传递依赖"，
  不依赖直接边图是否完整，因此**没有图截断偏差**。
* **级联深度**：`depth(v) = max over 依赖者 u of v: 1 + depth(u)`。
  在凝缩 DAG 上按**前向拓扑序**做一次 DP（此顺序写反会让所有深度变成 0 或 1，
  本项目自查时踩过这个坑，已在代码注释里标明）。
* **反向可达 + 加权暴露**：15718 × 246 的 `uint64` 位集矩阵（31 MB），
  沿前向拓扑序把依赖者的可达集向上合并；一次算完，落盘供实验四复用。
* **两种 PageRank，含义相反，分开命名**：
  * `pagerank_importance` = 在依赖流图 G 上算（"被越多重要的包依赖"）→ **瓶颈分数**
  * `pagerank_inherited` = 在反向图 G^R 上算（"它依赖了多少重要包"）→ **风险继承**
  * 这两者在本项目数据上 Spearman **−0.065**，**几乎正交**，方向搞反会得到相反的结论。
* **介数**：k=2000 点采样近似（精确介数 O(VE)≈7×10⁸，在纯 Python 里不可行），
  报告 k 与随机种子。

### 6.2 实验四：韧性情景（`src/23_exp_resilience.py`）

* 7 种移除策略 × 11 个移除比例 × 2 种失效规则；随机策略重复 **30 次**并报 ±1 s.d.
* 四个评价指标（**故意分开**，因为它们的形状与方向不同）：
  1. `S(q)` = 仍完全可用的种子包比例（**断崖型**）
  2. `avail_frac(q)` = 平均**仍存活**的闭包成员比例（连续型，**越大越好**）
  3. `loss_frac(q)` = `1 − avail_frac`（连续型，**越大越糟**）
  4. `LCC(q)` = 剩余网络最大弱连通分量份额（**与课程地铁案例同口径**）

  > **口径修正（评审意见 C-01）**：早期版本只输出一个名为 `availability_and` 的字段，
  > 但它存的其实是 `1 − 存活比例`，也就是**损失比例**——名字与内容相反。
  > 现在两种方向都显式命名（`avail_frac_*` 与 `loss_frac_*`），
  > 图表与正文也统一标"存活比例 / 损失比例"，不再混用"可用率"这种含糊说法。
  >
  > 这个错误**没有污染任何已公开结论**：该字段从未被任何图表或正文引用。
  > 危害是"未来会用错"，所以按严重程度它低于 B-01 / B-02。

* **情景 R 的暴露量用动态宽度**（评审意见 C-02）：
  `breadth_dyn(p) = |reverse_reach(p) ∩ 当时仍存活的节点|`，
  用位集一次 popcount 算出（`common.mask_to_bits` + `common.popcount_bits`）。
  旧口径（原始图上的静态宽度 `n_transitive_dependents`）保留为 `exposure_remove_static`，
  用来量化这次修正确实改了多少。原因：一边说生态被打碎、一边又把碎掉的依赖者算成风险，
  逻辑上自相矛盾。

* **第三种治理动作「保护」**（评审意见 C-03，`src/28_exp_protection.py`）：
  被保护的包**不会因为自己的依赖坏掉而失效**（钉版本 / vendor / CI 校验哈希），
  相当于图里的**防火墙节点**，直接切断级联路径。
  对照：破坏预算 q 固定 × 保护额度 k 固定 × `{保护枢纽, 随机保护, 无保护}`，
  每个对照排除一种具体的替代解释。

* **排序更新协议**（评审意见 B-02）：比较 **5 种协议**——
  `fixed` / `adaptive_staged` / `adaptive_staged_with_cascade` /
  `adaptive_per_node` / `adaptive_per_node_with_cascade`，见 `src/26_exp_adaptive.py`。

  > **一处必须纠正的错误论证**：早期版本写过"入度排序对移除不变，
  > 所以固定与自适应**在数学上等价**"。**这是错的**：删掉 u 会删掉边 `u→v`，
  > 于是 **v 的入度减 1**（反例：`A→B, C→B`，删 A 后 B 的入度 2→1）。
  > 现在脚本启动时跑这个反例自检，不成立就退出；
  > 结论的措辞也改成"**在本节的协议粒度与本样本上观察到的差异是……**"。
  > 逐点协议只对入度实现（其余指标每删一个包就要重算 PageRank/介数，成本不可接受），
  > 这一点写在 `t26_protocol_check.json` 里，**不假装已做**。

### 6.3 实验三：三级口径（`src/22_exp_vuln_tiers.py`）

见 `03_结果.md` §3。核心是引入了**反事实口径 F**（"假设漏洞至今未修复"），
把"过近似"拆成可归因的两段。

### 6.4 对照实验：保度序列零模型（`src/24_exp_nullmodel.py`）

* **有向双边交换**（double edge swap）：随机选两条边 `(a→b),(c→d)`，
  提议 `(a→d),(c→b)`，检查无自环/无重复后执行。
  精确保持每个节点的入度与出度，只随机化"谁连谁"。**脚本内 `assert` 逐点校验度序列**。
* 每条约 8 次成功交换，共约 33 万次 ⇒ 随机化充分。重复 **20 次实现**，
  所有结果报均值 ± 标准差与分位数分布（评审意见 D-02：原来只有 3 次，样本太薄）。
* **两个零模型族**（评审意见 D-01，本项目最大的方法学改进）：

  | 族 | 构造 | 为什么要它 |
  |---|---|---|
  | `degree` | 朴素保度双边交换 | 复现经典做法，也复现它的问题 |
  | `cycle_pres` | **保序**交换：按真实图凝缩拓扑序给每个节点一个全局序键；交换后两条新边都必须"序键向前"；原本在 SCC 内部（可能向后）的边**冻结**不参与交换 | 朴素交换会破坏无环性：真实图最大 SCC 只有 8 个节点，随机化后能长出 **361–601** 个节点的巨型 SCC，纯靠人造环抬高反向可达集 |

* **两个口径**：反向可达的**节点数**（经典，对大 SCC 敏感）与**凝缩类数**
  （每个 SCC 记 1，把人造放大压成 1）。四组合全部报告，判据事先声明：
  **任一结论若只在朴素族成立，就当作环伪影撤回。**

### 6.5 零模型的正确性检查

三件事分开做，因为它们是**不同层级**的校验：

1. **实现级**：位集实现（`src/23`）与 BFS 实现（`src/24`）在**同一移除集合**上给出
   逐位相同的 S(q)（最大差 1.1×10⁻¹⁶）。两个结构完全不同的实现互相印证。
2. **约束级**：零模型的度序列由 `assert` 逐点校验（`Gr.in_degree() == Gt.in_degree()`），
   不成立就直接抛异常，**不产出"看起来正常"的错误结果**。
3. **数据级**：闭包口径与图口径在**同一总体**上的集合比对（`src/11`）。
   这三层不能互相替代——第 1 层证明算法对，第 3 层才触及数据对。

## 附录 A · 九个踩过的坑（全部已修正，保留在此以便复现时避坑）

按"发现的难度"排序。**A.1–A.6 是我们自己发现的，A.7–A.9 是外部评审指出后确认的**——
后者更值得记，因为它们说明"内部互校"有盲区。

### A.1 位集展开的 bitorder（最隐蔽）

位集打包用 `word[i>>6] |= 1 << (i & 63)`，而 `np.unpackbits()` **默认按 MSB-first
展开每个字节**，会把每个字节内的 8 个位**倒序**输出。后果：

* **集合大小（popcount）完全正确** → 「级联规模」这类指标完全看不出异常；
* **集合成员与位置全部错乱**（每个 64 位块内被置换）→
  「加权暴露量」与「按位置取值的布尔掩码」全错。

三道防线都没抓住它：popcount 与闭包口径吻合（Spearman 0.971）、曲线单调合理、
数字看起来很像那么回事。最终是拿 `nx.ancestors` 做**集合级**（而非 popcount）
交叉验证才暴露。修法是 `bitorder="little"`（见 `common.bits_to_mask`）。

**方法论教训**：用"同一口径的两个实现互校"是不够的——当两个实现共享同一个错误的
抽象（都只比较 popcount），互校会一致地错。必须引入**结构不同**的第三方校验
（这里是 networkx 的 BFS）。修复后 `weighted_exposure` 与 `in_degree` 的
Spearman 从 0.821 变成 **0.971**，这本身就是"原来错了"的证据。

### A.2 `nan` / `null` / `none` 是合法包名

pandas 的默认 NA 规则会把它们读成缺失值，于是包**静默消失**；
更糟的是第一版把一个包名变成 `float('nan')` 送进 API，
deps.dev 居然真的解析到一个叫 `nan` 的包，数据里多了一条假记录。
修法：全局 `keep_default_na=False, na_values=[""]`（见 `common.read_csv_safe`）。

### A.3 PageRank 方向

在反向图 `G.reverse()` 上跑 PageRank 得到的是"**风险继承**"（我依赖了多重要的包），
不是"**瓶颈重要性**"（我被多重要的包依赖）。两者在本数据上 Spearman = −0.07，
**方向搞反会把结论整个说反**。修法：两个量分开命名（`pagerank_importance` /
`pagerank_inherited`）并写进 README 的口径表。

### A.4 级联深度 DP 的拓扑序方向

`depth(v) = max over 依赖者 u of v : 1 + depth(u)`，需要先算依赖者，
而依赖者在拓扑序里更靠前 ⇒ 必须用**前向**拓扑序。写反会让所有深度塌成 0 或 1。
抓它的方法：用一个 chain 结构手算对照。

### A.5 零模型的边列表来自 `set`

字符串哈希随机化让 `set` 的迭代顺序跨进程不稳定，同一 seed 在不同进程里会得到
约 0.02% 不同的结果。修法：`randomize_edges()` 里先 `sorted(edges)`，
并在 `run_all.ps1` 里固定 `PYTHONHASHSEED=0`。

### A.6 对照实验的平局排序与随机基准顺序

* 实验四与零模型对照原来分别用 pandas `sort_values` 与另一套排序，
  在大量同值节点上顺序不同，导致同一 q 上 S(q) 差 0.015。
  统一改成 `common.rank_by()`（同值按名称字典序破平局）。
* `random` 策略的 `rng.permutation` 必须基于同一节点顺序
  （统一为 `reach_nodes.json` 的顺序），否则同 seed 也不可比。

修完后，实验四（位集实现）与零模型对照（BFS 实现）在**同一移除集合**上
**逐位一致，最大差 1.1×10⁻¹⁶** —— 两个结构完全不同的实现互相印证，
这是"对照条件真正成立"的实测证据。

### A.7 把"闭包口径 vs 图口径"当成同一总体相减（评审 A-02 / B-03 指出）

\* 表现：一张表把"闭包口径 N（只数 14,992 个种子）"与"图口径 M（15,780 个节点）"并列，
然后解释"图口径系统性低估约 2%"。

\* 为什么错：这是**两个不同总体相减**。差异里混着三样东西——
总体不同、榜外叶子没有出边（截断）、声明层回退边（多边）。把它们一律归给"叶子截断"是过度解释。

\* 修法：新增 `src/11_closure_vs_graph.py`，把总体对齐成"图内种子"，
对每个包比较 `A(v) = {s : v ∈ closure(s)}` 与 `B(v) = {s : s 反向可达 v}` 两个**集合**，
分别报 `only_closure`（漏层）、`only_graph`（多边）、Jaccard、有符号差与**绝对差**分位数，
并加"只保留严格完整种子"的敏感性变体。

### A.8 把口径收缩写成因果归因（评审 B-01 指出）

\* 表现：README 写"98.9% 的高估来自依赖者早已升级越过修复版本"，
而同一份报告的另一处写"版本推进只解释了 9.47%"。

\* 为什么错：**两处都超出了数据能支持的范围**，而且互相矛盾。
我们只有当期快照，没有时间序列，因此**无法观察谁在何时升级**。
F→V 的差集在单区间 advisory 上**恒等于** `resolved ≥ fixed`——那是**定义恒等式**，不是机制发现。

\* 修法：`t22_decomposition.csv` 的列名从 `收缩归因` 改为
`相对上一口径的收缩` + `这一步改动了什么（口径事实，非因果归因）`；
`t22_summary.json` 的键 `attrib_upgrade`/`attrib_patch` → `shrink_S_to_F`/`shrink_F_to_V`，
并新增 `attribution_note`；正文统一成"每个百分比写清分母 + 明确声明不可归因"。

\* **这一类错误比算错更难发现**：算错会让数字长得奇怪，归因错会让数字**长得非常漂亮**。

### A.9 把"没做的实验"说成"数学定理"（评审 B-02 指出）

\* 表现：文件头注释写"删除其他节点不改变入度，所以固定与自适应排序**在数学上等价**"。

\* 为什么错：图里 `u→v` 表示 u 依赖 v，删掉 u 就删掉了边 `u→v`，于是 **v 的入度减 1**。
反例：`A→B, C→B`，删掉 A 后 `in_degree(B)` 从 2 变 1。

\* 修法：脚本启动时跑这个反例自检（不成立就 `SystemExit`）；实现 5 种协议，
其中包括**严格逐点**版本（每删一个包就重排）；结论措辞降级为
"在本节的协议粒度与本样本上观察到的差异是……"。

\* 这一类错误的危害是**它让一个本该实测的问题免于检验**，
比"算错一个数"更严重。
