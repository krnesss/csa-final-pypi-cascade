**为什么不用 PyPI 的 `requires_dist` 直接建图？**
PyPI 元数据写的是 PEP 508 的**约束表达式**（`urllib3>=1.21.1,<3`），不是解析结果。
直接用它建图有三个问题：条件依赖（`; extra == 'test'`、`; python_version<'3.8'`）、
同一生态内不同包的版本需求互相冲突（版本求解）、以及最关键的——**我们无法知道
"某个包实际会装到哪个版本"，于是无法做版本感知的级联判定**。
deps.dev 返回的是**一个具体版本**的已完成解析闭包，节点带 `DIRECT/INDIRECT`
关系与解析后的确切版本号，正好补上这一环。

**覆盖率与失败记账**（不静默丢弃任何东西）：

| 项目 | 数量 | 占比 | 处理 |
|---|---|---|---|
| 种子包总数 | 15,000 | 100% | — |
| deps.dev 给出已解析闭包 | 14,468 | 96.5% | 主口径 |
| deps.dev 无解析结果（404），回退到 PyPI `requires_dist` | 525 | 3.5% | 标记 `deps_status=unresolved`；闭包**只有一层**，在广度统计中会**低估**，故单独记账 |
| 包在 deps.dev 上不存在（已删除 / 测试夹具，如 `piot-fixture-*`、`aaaaaaaaa`） | 7 | 0.05% | 从图中缺席，不参与任何统计 |

## 2. 时间切片的定义（把"固定切片"变成可审计的事实）

依赖关系是动态的，题目也点出了这个难点。本项目的切片定义为：

```
时间切片 ≡ ( 下载量榜的统计月份 , 每个包被解析到的具体版本号 )
```

* 下载量榜自带 `last_update`（本项目为 `2026-11-01`），写入 `universe.csv` 每行；
* **每个包被解析到的确切版本号逐包落盘**（`universe_coverage.csv` 的 `resolved_version`；
  `closures.parquet` 里每个依赖的 `dep_version`）。

因此这一张网可以在任何时候用同一批版本号重建，不依赖"抓取那天"的服务器状态。
这是把"依赖是动态的"这一难点处理成可检验事实的关键一步。

## 3. 网络模型

### 3.1 节点

```
N = S ∪ T
S = 下载量榜前 15,000 名（有 7 个在 deps.dev 上不存在，实际 14,993）
T = 出现在种子闭包里但不在榜上的包（本项目仅 725 个）
```

`T` 只占 4.6%，说明**榜内 15,000 个包已经互相闭合了 99.5% 的依赖闭包**
（`frac_closure_nodes_in_universe = 0.9947`）。这是个好消息：我们的截断偏差很小，
但它仍然被量化并报告（见 §5）。

### 3.2 边

```
边 (u → v) 存在 ⟺ 包 u 的直接依赖声明里包含包 v
```

* **方向 = 依赖流方向**（u 依赖 v）。
* **级联传播方向相反**：v 出问题 → 沿 v → u 传播。报告里每次说"上游/下游"都会显式标注。
* **只保留直接边**。deps.dev 的闭包同时给出 `DIRECT` 与 `INDIRECT`；
  如果把 `INDIRECT` 也当作边，图会退化成近团状，所有中心性指标被压平。
* 自环剔除。

### 3.3 权重

* 节点权重 = 该包的月下载量；榜外包无数据，**显式置为缺失而不是 0**，
  在加权指标里排除（不臆造）。
* **边不加权**：deps.dev 不提供"用了多少"的信息。我们不臆造权重，
  并在局限性里说明这会**高估**弱依赖的影响。

### 3.4 简化假设清单（必须显式声明）

| 简化 | 处理 | 偏差方向 |
|---|---|---|
| 依赖强度 | 不加权 | 高估弱依赖的影响 |
| 可选依赖 | 剔除 `extra == ...` 的条件依赖 | 低估"装了某 extra 才触发"的漏洞 |
| 版本 | 用**已解析的具体版本**，不是声明区间 | 是"解析器的选择"，不是"每个用户实际装的" |
| 多版本共存 | 一个包一个节点 | 高估共现 → 高估结构口径影响（该偏差已被实验三量化） |
| 方法级可达性 | **不做到** | 版本脆弱 ≠ 代码真调用，我们的"现实影响"仍是**上界** |
| 时间 | 单层静态快照 | 结论只对该切片成立（用时间外推检验 §6.2 检查稳健性） |
| 环 | 允许（实测 20 个 SCC，最大 8 个节点） | 来自条件依赖互相引用；用 SCC 凝缩做精确处理 |

## 4. 三种级联规则（题目要求"传播规则需要自己定义"）

| 规则 | 定义 | 现实对应 | 用途 |
|---|---|---|---|
| **R_AND（合取）** | 包的**任一**直接依赖不可用 ⇒ 包不可用 | **软件的真实语义**：缺一个依赖就 build 失败 | 主口径；失败集合 = 被移除集合的反向可达并集 |
| **R_OR（析取）** | 包的**全部**直接依赖不可用 ⇒ 包不可用 | **食物网的次级灭绝语义**：捕食者失去全部猎物才灭绝 | 对照；用"存活依赖计数 + 队列"迭代求解，O(V+E) |
| **R_VULN（漏洞）** | 包的传递闭包里存在受影响的包 ⇒ 包受影响 | 依赖扫描 | 分三级口径（结构 / 反事实 / 现实），见 §6.3 |

**这是本项目的核心论点之一**：把食物网的级联模型直接搬到软件上会
**系统性低估**软件生态的脆弱性，因为软件是"与门"而非"或门"。
在 §6.4 里这个差异被量化成了 40 个百分点的 S(q) 差距。

### 5.1 一个真实踩过的数据清洗坑（值得写进报告）

PyPI 上**真的存在**名为 `nan`、`null`、`none` 的包。pandas 的默认 NA 规则
（`keep_default_na=True`）会把 `null` / `none` / `nan` 读成缺失值 `NaN`。
后果非常隐蔽：

1. 这个包从图里**静默消失**，不报错、不影响任何指标"长相"；
2. 更糟的是，我们在第一版里把一个包名变成了 `float('nan')` 送进 API，
   **deps.dev 居然真的解析到了一个叫 `nan` 的包**，于是数据里多了一条假记录。

修复方式是全局 `keep_default_na=False, na_values=[""]`，并把 `nan/null/none`
三个包补抓回来。这正是题目所说"数据清洗比交通/金融数据更琐碎"的一个具体样本。

### 5.2 第二个坑：零模型的边顺序导致"不完全可复现"

双边交换的起点是一个 `set[tuple[str, str]]`。Python 的字符串哈希在每个进程里
加盐随机化，因此 `list(some_set)` 的顺序**跨进程不稳定**。后果是：同一 random seed、
同一份数据，在不同进程里跑出的零模型结果会相差约 **0.02%**——不报错、不影响定性结论，
但违反"逐位可复现"。

修法两处：

1. `randomize_edges()` 里先 `sorted(edges)` 建立确定性的初始边列表；
2. `run_all.ps1` 里固定 `PYTHONHASHSEED=0`。

修完后两次独立运行结果**逐位相同**（实测 `null_mean` 三次实现为 564.27 / 627.01 / 424.67，
两次运行完全一致）。这一点是本项目"材料可复现"这一项的实测证据，而不是声明。

### 5.3 第三个坑：`set` 迭代顺序也影响观察本身

本项目还踩过一个更隐蔽的同类问题：`nx.pagerank(G.reverse())` 方向搞反会得到
"风险继承"而不是"瓶颈重要性"（两者在本数据上 Spearman −0.065，几乎正交）。
这类错误不会报错、指标看起来也"像那么回事"，只能靠**语义自查**发现。
我们因此把两个量分开命名并写进 README 的口径表，避免后人也踩。

## 6. 实验设计与实现要点

### 6.1 实验二：指标计算（`src/21_exp_cascade.py`）

* **精确广度**：用 deps.dev 的已解析闭包直接统计"被多少种子包传递依赖"，
  不依赖直接边图是否完整，因此**没有图截断偏差**。
* **级联深度**：`depth(v) = max over 依赖者 u of v: 1 + depth(u)`。
  在凝缩 DAG 上按**前向拓扑序**做一次 DP（此顺序写反会让所有深度变成 0 或 1，
  本项目自查时踩过这个坑，已在代码注释里标明）。
* **反向可达 + 加权暴露**：15718 × 246 的 `uint64` 位集矩阵（31 MB），
  沿前向拓扑序把依赖者的可达集向上合并；一次算完，落盘供实验四复用。
* **两种 PageRank，含义相反，分开命名**：
  * `pagerank_importance` = 在依赖流图 G 上算（"被越多重要的包依赖"）→ **瓶颈分数**
  * `pagerank_inherited` = 在反向图 G^R 上算（"它依赖了多少重要包"）→ **风险继承**
  * 这两者在本项目数据上 Spearman **−0.065**，**几乎正交**，方向搞反会得到相反的结论。
* **介数**：k=2000 点采样近似（精确介数 O(VE)≈7×10⁸，在纯 Python 里不可行），
  报告 k 与随机种子。

### 6.2 实验四：韧性情景（`src/23_exp_resilience.py`）

* 7 种移除策略 × 11 个移除比例 × 2 种失效规则；随机策略重复 **30 次**并报 ±1 s.d.
* 三个评价指标（**故意用三个**，因为它们的形状不同）：
  1. `S(q)` = 仍完全可用的种子包比例（**断崖型**）
  2. `availability(q)` = 平均仍存活的闭包成员比例（**连续型**）
  3. `LCC(q)` = 剩余网络最大弱连通分量份额（**与课程地铁案例同口径**）
* **排序更新协议**：默认按初始网络固定排序；另在 `src/26_exp_adaptive.py` 里
  做"每步重算"的敏感性对照。
  并给出一个**结构性断言**：入度排序对"移除其他节点"是**不变**的
  （删掉节点 v 只删指向 v 的边，不改变任何其他节点的入度），
  因而 in-degree 的固定/自适应排序**在数学上等价**——实测 Δ ≤ 0.0007，验证了该断言。

### 6.3 实验三：三级口径（`src/22_exp_vuln_tiers.py`）

见 `03_结果.md` §3。核心是引入了**反事实口径 F**（"假设漏洞至今未修复"），
把"过近似"拆成可归因的两段。

### 6.4 对照实验：保度序列零模型（`src/24_exp_nullmodel.py`）

* **有向双边交换**（double edge swap）：随机选两条边 `(a→b),(c→d)`，
  提议 `(a→d),(c→b)`，检查无自环/无重复后执行。
  精确保持每个节点的入度与出度，只随机化"谁连谁"。
* 实测每条约 7.0 次成功交换（成功率 87%），共约 33 万次成功交换 ⇒ 随机化充分。
* 允许零模型出现环（"v 坏 ⇒ 所有依赖者坏"这条规则不需要无环），
  因此只在零模型上报告 AND 规则。

### 6.5 零模型的正确性检查

真实网络上，零模型口径与闭包口径的广度 Spearman = 0.971，
说明两套实现（闭包 vs 图位集）互相独立地给出了一致结果。

## 附录 A · 六个踩过的坑（全部已修正，保留在此以便复现时避坑）

按"发现的难度"排序。

### A.1 位集展开的 bitorder（最隐蔽）

位集打包用 `word[i>>6] |= 1 << (i & 63)`，而 `np.unpackbits()` **默认按 MSB-first
展开每个字节**，会把每个字节内的 8 个位**倒序**输出。后果：

* **集合大小（popcount）完全正确** → 「级联规模」这类指标完全看不出异常；
* **集合成员与位置全部错乱**（每个 64 位块内被置换）→
  「加权暴露量」与「按位置取值的布尔掩码」全错。

三道防线都没抓住它：popcount 与闭包口径吻合（Spearman 0.971）、曲线单调合理、
数字看起来很像那么回事。最终是拿 `nx.ancestors` 做**集合级**（而非 popcount）
交叉验证才暴露。修法是 `bitorder="little"`（见 `common.bits_to_mask`）。

**方法论教训**：用"同一口径的两个实现互校"是不够的——当两个实现共享同一个错误的
抽象（都只比较 popcount），互校会一致地错。必须引入**结构不同**的第三方校验
（这里是 networkx 的 BFS）。修复后 `weighted_exposure` 与 `in_degree` 的
Spearman 从 0.821 变成 **0.971**，这本身就是"原来错了"的证据。

### A.2 `nan` / `null` / `none` 是合法包名

pandas 的默认 NA 规则会把它们读成缺失值，于是包**静默消失**；
更糟的是第一版把一个包名变成 `float('nan')` 送进 API，
deps.dev 居然真的解析到一个叫 `nan` 的包，数据里多了一条假记录。
修法：全局 `keep_default_na=False, na_values=[""]`（见 `common.read_csv_safe`）。

### A.3 PageRank 方向

在反向图 `G.reverse()` 上跑 PageRank 得到的是"**风险继承**"（我依赖了多重要的包），
不是"**瓶颈重要性**"（我被多重要的包依赖）。两者在本数据上 Spearman = −0.07，
**方向搞反会把结论整个说反**。修法：两个量分开命名（`pagerank_importance` /
`pagerank_inherited`）并写进 README 的口径表。

### A.4 级联深度 DP 的拓扑序方向

`depth(v) = max over 依赖者 u of v : 1 + depth(u)`，需要先算依赖者，
而依赖者在拓扑序里更靠前 ⇒ 必须用**前向**拓扑序。写反会让所有深度塌成 0 或 1。
抓它的方法：用一个 chain 结构手算对照。

### A.5 零模型的边列表来自 `set`

字符串哈希随机化让 `set` 的迭代顺序跨进程不稳定，同一 seed 在不同进程里会得到
约 0.02% 不同的结果。修法：`randomize_edges()` 里先 `sorted(edges)`，
并在 `run_all.ps1` 里固定 `PYTHONHASHSEED=0`。

### A.6 对照实验的平局排序与随机基准顺序

* 实验四与零模型对照原来分别用 pandas `sort_values` 与另一套排序，
  在大量同值节点上顺序不同，导致同一 q 上 S(q) 差 0.015。
  统一改成 `common.rank_by()`（同值按名称字典序破平局）。
* `random` 策略的 `rng.permutation` 必须基于同一节点顺序
  （统一为 `reach_nodes.json` 的顺序），否则同 seed 也不可比。

修完后，实验四（位集实现）与零模型对照（BFS 实现）在**同一移除集合**上
**逐位一致，最大差 1.1×10⁻¹⁶** —— 两个结构完全不同的实现互相印证，
这是"对照条件真正成立"的实测证据。
