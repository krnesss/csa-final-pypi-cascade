### B-02｜"固定 vs 自适应入度等价"是错误论证 —— 采纳

**问题确认**：图里 `u→v` 表示 u 依赖 v，因此删掉 u 会删掉边 `u→v`，**v 的入度减 1**。
我们原来在 `src/26_exp_adaptive.py` 文件头写的"入度排序对移除不变，所以两者数学等价"是错的。

**改了什么**

1. **删掉错误断言**，改成"在本实验的分阶段重排序粒度下比较固定与更新"，并明确写成经验观察而非定理。
2. **加一个自检**：`src/26_exp_adaptive.py` 启动时构造 `A→B, C→B`，删除 A 后断言 `in_degree(B)` 由 2 变 1；
   不成立就直接 `SystemExit`。结果写入 `t26_protocol_check.json` 的 `self_check_indegree`。
3. **新增五种协议**（原来只有两种）：
   `fixed` / `adaptive_staged` / `adaptive_staged_with_cascade` /
   `adaptive_per_node` / `adaptive_per_node_with_cascade`。
   其中 `adaptive_per_node` 是评审要求的**严格版本**——每删除**一个**包就重算入度排序，
   并用增量维护（删 u 时把它后继的计数减 1，总代价 O(E)），所以它真的跑得动。
   `_with_cascade` 变体回答评审的第 4 问：**级联失效的包是否同时从排名图里移除**。
4. **输出 Top-k 重合度**（Top-10/20/50/79/100/200，Jaccard + 命中数），并输出一个**测量出来的解释**：
   瓶颈榜前 79 名的平均出度只有约 1.9（其中 38 个出度为 0），删掉它们只触碰全部 47,944 条边里的约 151 条，
   所以入度排名几乎不动。**这是观测结果，不是先验推导**。
5. `t26_protocol_check.json` 里写了一条 `wording_rule`：结论只能写成"在本样本与本协议粒度下观察到的差异"。

**说明（保留意见）**：`adaptive_per_node` 只对 `by_in_degree` 实现。其余指标每删一个包就要重算
PageRank / 介数，成本不可接受。这一点在 `t26_protocol_check.json` 的 `note_protocol_scope` 里写明，
**不假装已做**。

**验证**：`python tests/test_small_graphs.py`（T7 组）；`results/tables/t26_protocol_check.json`；
`results/tables/t26_adaptive_pivot.csv`。

### C-02｜移除后的暴露量没有重算存活依赖者 —— 采纳（结论方向不变，但确实自相矛盾）

**问题确认**：`t23_patch_vs_remove.csv` 的 `exposure_remove` 用 `n_transitive_dependents`
（**原始图**上的静态宽度）做权重，于是"已经被移除打断的依赖者"仍在计入暴露量。
一边说生态被打碎、一边又把碎掉的依赖者算成风险，逻辑上自相矛盾。

**改了什么**：情景 R 改用**动态宽度**

```
breadth_dyn(p) = |reverse_reach(p) ∩ 当时仍存活的节点|
```

用位集实现（`common.mask_to_bits` + `common.popcount_bits`），成本是每个包一次 popcount。
同时**保留旧口径**为 `exposure_remove_static` 与 `exposure_remove_static_drop_pct` 两列，
把"口径修正到底改了多少"变成可查的量，而不是一句口头说明。另新增
`n_vuln_sources_patch` / `n_vuln_sources_remove`（仍作为漏洞源的包个数）。

**下调理由**：修正只会让 `exposure_remove` **更小**（去掉已经不存在的依赖者），
而正文的结论是"移除比修复造成的损失大得多"（因为 S_after_remove 塌了），
所以修正是**加强**而不是推翻该结论。因此严重程度低于 P0。

**验证**：`results/tables/t23_patch_vs_remove.csv` 的 `exposure_remove` 与
`exposure_remove_static` 两列对比；`common.popcount_bits` 的往返测试见
`tests/test_small_graphs.py` T3 组。

### A-02｜多版本合并可能引入假传递路径 —— 采纳

**问题确认**：把 `(seed, dep)` 按**包名**合并成一个图，确实可能造出"实际解析闭包里并不存在"的路径
（A 用 `B==1.0`、C 用 `B==2.0`，只有 2.0 依赖 D，包名图里就同时有 `A→B`、`C→B`、`B→D`）。
评审更关键的一句是：**原报告那张"闭包口径 vs 图口径"的表是两个不同总体相减**
（闭包只数 14,992 个种子，图数 15,780 个节点），所以那张表不能用来归因于错误边。

**改了什么**：新增 `src/11_closure_vs_graph.py`，把总体**对齐**到"图内种子"这一个共同集合，
对每个包 v 比较两个集合

```
A(v) = { s ∈ S : v ∈ closure(s) }        （闭包口径）
B(v) = { s ∈ S : s 在图中反向可达 v }     （图口径）
```

输出 `FP = |A∖B|`（闭包说有、图说没有 = 图漏层/叶子截断）、
`FN = |B∖A|`（图说有、闭包说没有 = 声明层回退引入的边或包名合并造成的假路径）、
Jaccard、有符号差、绝对差。并按评审第 5 条做了**敏感性变体**：
`all_graph_seeds` vs `strict_complete_seeds_only`（只保留严格完整的种子），
比较两个变体下的 Spearman 与 Top-20 榜单重合。

`report/03` 的相应段落改为：不再把 Spearman=0.971 当成"逐个包影响面精确"的证据，
而是明确写"两者在**排序**上高度一致、在**绝对数**上的差异被分解为叶子截断与回退边两类"。

**验证**：`results/tables/t11_closure_vs_graph.csv`、
`results/tables/t11_closure_vs_graph_summary.json` 的 `sensitivity` 与 `top20_disagreements`。

### B-04｜中心性方向与稳定性 —— 采纳

**问题确认**：介数用 `k=2000` 的**抽样近似**，Top 名次不稳；PageRank 的方向容易写反。

**改了什么**

1. **主流程改用精确全源介数**：`config.yaml` 的 `betweenness_k` 设为 `0`（0 = 无采样）。
   实测本图（15,780 节点 / 47,944 边）精确介数约 **50 秒**——也就是说"精确不可行"这个
   前提假设本身就是错的。
2. 新增 `src/27_exp_centrality_stability.py`：对 `k ∈ {500,1000,2000} × seed ∈ {7,101,2024}`

   以及**同 k 不同 seed 之间**的 Top-N 重叠。产出
   `t27_betweenness_stability.csv` / `t27_betweenness_seed_overlap.csv` / `t27_betweenness_runtime.json`。
   —— 这正好是评审建议的"至少两组不同随机种子下输出 Top10 重合数与 Spearman"。
3. **方向写清**：`README.md` 的「关键口径」表新增一行，明确
   `in_degree(v)` = 直接依赖 v 的包数、`out_degree(v)` = v 直接依赖的包数，
   **不能反过来**；`pagerank_importance` 算在依赖流图 G 上（"被谁依赖"），
   `pagerank_inherited` 算在反向图（"依赖了谁"），两者几乎正交。
   最终结论用的 Top 榜单按**代码方向**命名，不按中文直觉命名。

### C-03｜"修复包"不是"保护关键包" —— 采纳（拆分处理）

**问题确认与判断**：`question.txt` 的原话是"关键包被修复 **或** 关键包被移除"——
这两个动作已由 `src/23` 的情景 P / R 完成，所以题面本身**没有**要求"保护"。
但课程分工里写了"保护"，而"保护"在依赖网络上有独立含义：

| 动作 | 语义 | 谁来算 |
|---|---|---|
| 修复 patch | 包还在、结构不变，只是它自己不再引入漏洞 | `src/23` 情景 P |
| 移除 remove | 包从注册表消失，依赖它的东西全部构建失败 | `src/23` 情景 R |
| **保护 protect** | 钉版本 / vendor / CI 校验哈希 ⇒ **即使它自己的依赖坏掉，它也不会跟着坏** | **新增 `src/28`** |

**改了什么**：新增 `src/28_exp_protection.py`。被保护的包相当于依赖图里的**防火墙节点**：
故障撞上来就到此为止。脚本按固定破坏预算 q（`targeted` / `random` 两种破坏模式）
× 保护额度 k ∈ {10,20,50,100,200,500} × `{保护枢纽, 随机保护, 无保护}` 计算存活种子比例，
并给出"枢纽保护相对随机保护的 ΔS 增益"。**每个对照都排除一种具体替代解释**：
破坏 q 固定 ⇒ 排除"保护有效只是因为破坏变少"；保护额度 k 固定 ⇒ 排除"只是因为多保护了几个"；
`protect_random` ⇒ 排除"任何 k 个包都行、枢纽排名没用"；`k=0` ⇒ 排除"提升来自模型本身"。

脚本启动时还做一次**交叉校验**：保护集为空时，逐点 BFS 传播的结果必须与实验四的位集并集
**逐位相同**，否则直接 `SystemExit`（不产出错误结果）。

**验证**：`results/tables/t28_protection_curves.csv` / `t28_protection_summary.csv` /
`t28_protection_gain_ratio.csv`；一致性校验在 `t28_protection_check.json` 的
`cross_check_vs_bitset`（5 组随机破坏，全部 `equal: true` 才继续）。

### C-04｜AND/OR 规则、广度、深度的边界说明 —— 采纳

**改了什么**

1. **规则边界**（`report/02` §2.3 已扩写）：
   * `R_AND`：**任一必需依赖失败 ⇒ 上游失败**。这是对"构建/可用性"的**简化模型**——
     可选依赖、替代实现（如 `pyOpenSSL` vs `ssl`）、运行期才走的分支都不满足这个假设。
   * `R_OR`：**全部直接依赖失败才失效**。它来自食物网的"次级灭绝"，
     用来展示**规则敏感性**，**不是** PyPI 的安装机制。我们只用它做对照，不用它下结论。
2. **广度口径统一**：`n_transitive_dependents` / `n_transitive_all_nodes` /
   `weighted_exposure` 三者**都不含源节点自身**，是"受影响的其他节点/种子数"。
   位集实现里显式做 `mask.sum() - 1`（见 `src/21_exp_cascade.py` 的 `reverse_reach`）。
3. **深度口径**：`cascade_depth` 定义为**凝缩图**上的最长反向路径跳数。
   有环时，同一个 SCC 内的所有成员共享同一个深度，SCC 内部不再区分（本项目 20 个非平凡 SCC、
   最大 8 个节点、占 0.33% 节点，影响可忽略但如实说明）。
4. **新增 3 个具体案例**（`src/12_cascade_cases.py`）：基础依赖包 / 中间库 / 边缘应用包，
   每类按**事先声明的规则**挑选（不是挑好看的），输出按跳数分层的扩散、
   以及 3 条**逐跳可核对**的真实依赖链。产出 `t12_case_studies.json` 与 `t12_case_paths.csv`。

**验证**：`report/02_数据与方法.md` §2.3、§3.4；`results/tables/t12_case_paths.csv`
（`edge_meaning` 列直接写着"X 直接依赖 Y"，可在 `edges.csv` 里逐条核对）。

### D-01｜保度随机网络会引入大环 —— 采纳（这一条是本项目最大的方法学改进）

**问题确认并量化**：真实图最大 SCC 只有 **8** 个节点（20 个非平凡 SCC，占 0.33% 节点），
而朴素保度双边交换能造出 **361–601** 节点的巨型 SCC（占 2.3–3.8% 节点）。
一个 601 节点的 SCC 意味着它的每个成员都能"反向到达"另外 600 个成员，
于是"真实网络比零模型脆弱得多"这个结论里混进了**两种效应**：
(1) 真实的度异质性（想测的）；(2) 零模型自身的巨型环（纯人造伪影）。

**改了什么**：跑**两个零模型族** × **两个口径**，共 4 条对照线。

| | 族 A `degree` | 族 B `cycle_pres` |
|---|---|---|
| 构造 | 朴素保度双边交换（复现经典做法，也复现这个问题） | **保序**双边交换：按真实图凝缩拓扑序给每个节点一个全局序键，交换后两条新边都必须"序键向前"，并把原本在 SCC 内部的（可能向后的）边**冻结**不参与交换 |
| 度序列 | 精确保持 | 精确保持（脚本内 `assert` 机器校验） |

| | 口径 ① `node` | 口径 ② `condensation` |
|---|---|---|
| 度量 | 反向可达的**节点**数（经典口径，对大 SCC 敏感） | 反向可达的**凝缩类**数（每个 SCC 记 1，把大 SCC 的人造放大压成 1） |

四种组合下都报告 `null_max_scc` / `null_n_scc`，于是"结论会不会只是环伪影"变成可查的数字。
判据写在 `report/03` 里：**任一结论若只在族 A 成立，就说明它其实是环伪影。**

**验证**：`results/tables/t24_null_compare.csv` 的 `family` / `metric` / `null_max_scc` 列；
`results/tables/t24_null_swaps.json`（含 `true_scc`、`true_backward_edges`、每族的冻结边数与
`rejected_backward` 计数）。

---

**实测结果（这一条改变了我们的主结论）**

| | 真实图 | 朴素族 `degree` | 保环族 `cycle_pres` |
|---|---|---|---|
| 最大 SCC（20 次实现中位数） | **8** | **484** | **2** |
| 反向可达均值 | **11.08** | **526.92 ± 94.85** | **20.53 ± 1.53** |
| 相对真实网络 | 1.00× | **47.6×** | **1.85×** |

分解：`真实 → 保环族 = 1.85×`（真实拓扑的贡献）+ `保环族 → 朴素族 = 25.7×`（纯人造环的贡献）。

因此本项目**撤回了上一版的两条结论**：

1. ~~"分层结构把级联压低了一个半到两个数量级"~~ → 改为"**1.85 倍量级的有限效应**"，
   朴素族的 45.6 倍里约 96% 是环伪影。
2. ~~"随机故障下真实生态比同度序列随机网络鲁棒近 6 倍"~~ → 撤回。
   q=1% 时真实 **0.920**、保环族 **0.871 ± 0.105**，差 4.9 个百分点。

**仍然成立的两条**（在两族零模型下都成立，所以不属于环伪影）：

* 反向可达规模的**排名一致性** ρ = 0.980（保环族）/ 0.959（朴素族）——
  "谁是枢纽由度序列决定"不受影响；
* **靶向移除下三者几乎重合**（q=0.5% 按入度移除：0.3751 / 0.3475 / 0.3512）——
  "如果对手知道该打谁，拓扑结构救不了你"。

**这一条是本轮评审里价值最高的一条**：它不是指出我们算错了一个数，
而是指出我们的**对照设计本身引入了伪影**。要发现它，必须追问
"这个零模型除了随机化我想随机化的东西，还随机化了什么？"

**验证**：`results/tables/t24_null_compare.csv`（`family` / `metric` / `null_max_scc` 三列）；
`results/tables/t24_null_swaps.json`（`true_scc`、`true_backward_edges`、每族冻结边数与
`rejected_backward` 计数）；`report/03_结果.md` §6.1 与 §8 的 H5/H6。
